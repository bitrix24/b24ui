## Upstream change

Five theme files, one string each. Reka publishes the space the popper actually
has as `--reka-<component>-content-available-height`; nothing was reading it, so
a dropdown near the bottom of the window overflowed. Upstream caps the `content`
slot with it:

```diff
# context-menu.ts, dropdown-menu.ts — no ceiling, just the available height
-    content: 'min-w-32 bg-default …'
+    content: 'min-w-32 max-h-(--reka-context-menu-content-available-height) bg-default …'

# input-menu.ts, select.ts — replace the fixed cap with min(existing, available)
-      content: 'max-h-60 w-(--reka-combobox-trigger-width) …'
+      content: 'max-h-[min(15rem,var(--reka-combobox-content-available-height))] w-(--reka-combobox-trigger-width) …'

# select-menu.ts — same cap, added to the composed content
```

`15rem` is `max-h-60`: upstream keeps its own ceiling and only adds the popper
bound underneath it. 381 lines move in ten snapshot files, all of them the class
attribute.

## b24ui port

**The idea ports; the strings do not.** The cap upstream adds to `content` was
already here — on a different slot. Every one of the five components carried
`max-h-[40vh]` on `viewport`, so applying upstream's hunks verbatim would have
left two independent caps fighting: an unconditional `40vh` inside a `content`
bounded by the available height, which clips at 40vh regardless of how much room
the popper actually has. The port therefore moves the cap rather than adding one:

```diff
# context-menu.ts / dropdown-menu.ts
+      'flex flex-col',
+      'max-h-[min(40vh,var(--reka-context-menu-content-available-height,40vh))]',   // content
-      'w-full max-h-[40vh] min-w-48',
+      'w-full min-w-48 flex-1',                                                     // viewport
```

Three differences from upstream, each with a reason:

- **The ceiling is ours, not upstream's.** `40vh` for the menus and `40rem` for
  the combobox/select family, because those are the caps this fork already shipped
  — adopting upstream's `15rem` would have silently shortened every dropdown in
  the library. Upstream's shape (`min(ceiling, available)`) is what was taken.
- **A fallback the upstream expression has no need for.** `var(--reka-…, 40vh)`
  and `var(--reka-…, 100vh)`: when reka does not set the variable, `min()` with an
  unresolved `var()` makes the whole declaration invalid and the cap disappears
  entirely. `Select` with `position="item-aligned"` is exactly that case — reka
  positions it itself and never publishes the available height. Upstream's menus
  use the bare `max-h-(--reka-…)` form, where an unset variable is merely no cap;
  in a `min()` it is a broken one.
- **`flex flex-col` on `content` and `flex-1` on `viewport`.** Upstream's
  `content` already had `flex flex-col`; ours did not, and without it the `max-h`
  on `content` binds nothing because the viewport does not shrink to it. This is
  the mechanical half of moving the cap between slots.

Two fixes are **ours and not in upstream at all**, found while touching these
files:

- `input-menu.ts` and `select.ts` read
  `origin-(--reka-dropdown-menu-content-transform-origin)` — the wrong component's
  namespace. A combobox never sets the dropdown-menu variable, so the scale
  animation had no transform origin. Corrected to `--reka-combobox-…` and
  `--reka-select-…`.
- `editor-suggestion-menu.ts` had the same dropdown-menu variable, but there the
  fix is different: that menu is positioned by tiptap/floating-ui rather than by
  reka, so *no* reka variable is ever set. It takes a static `origin-top`.

Also in the commit: `b24b24ui` → `b24ui` typos in the dropdown-menu docs page,
and a `.sync/PLAN.md` line (that file was deleted later, 2026-08-12).

## Breaking

**Breaking here, not upstream, and correctly so.** Upstream's cap was already on
`content`, so nothing about a consumer's overrides changed. Ours moved from
`viewport` to `content`: anyone who had overridden `b24ui.viewport` with a
`max-h-*` on Select, SelectMenu or InputMenu finds that override capping a slot
that is no longer the constraint. `5da53b6b` marks the subject
`fix(components)!` with a `BREAKING CHANGE:` footer naming the migration — move
the cap to `b24ui.content`, width overrides unaffected — which is what
release-please reads (§6).

788 lines move across ten snapshot files, roughly double upstream's, because both
slots change here rather than one.

## Verification (2026-08-30)

Checked against `main`. All five caps are in place and all six transform origins
are on their own namespace:

| file | cap | origin |
| --- | --- | --- |
| `context-menu.ts` | `min(var(--max-height-popup-menu), var(--reka-context-menu-…, var(--max-height-popup-menu)))` | `--reka-context-menu-…` |
| `dropdown-menu.ts` | same, dropdown-menu namespace | `--reka-dropdown-menu-…` |
| `input-menu.ts` | `min(var(--max-height-popup-list), var(--reka-combobox-…, 100vh))` | `--reka-combobox-…` |
| `select-menu.ts` | same | `--reka-combobox-…` |
| `select.ts` | `min(var(--max-height-popup-list), var(--reka-select-…, 100vh))` | `--reka-select-…` |
| `editor-suggestion-menu.ts` | — | `origin-top` |

The literal `40vh` and `40rem` are gone: `648cd19e` (#430, *feat(theme): tokenize
the popup height caps*) replaced them with `--max-height-popup-menu` and
`--max-height-popup-list`, defined in
`src/runtime/air-design-tokens/tw-style/sizes.css` and guarded by
`test/utils/popup-height-tokens.spec.ts`. The `min()` shape, the fallbacks and the
slot the cap sits on are all unchanged from this port.
