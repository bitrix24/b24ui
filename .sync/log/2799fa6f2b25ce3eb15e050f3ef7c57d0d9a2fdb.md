## Upstream change

`autocomplete` was a boolean prop, which collided with the native HTML attribute
of the same name — `InputMenuProps` had to `Omit<InputHTMLAttributes,
'autocomplete' | …>` to keep the two apart, so the native attribute could not be
forwarded to the input at all. The rename frees it:

```diff
-  autocomplete?: boolean
+  mode?: 'combobox' | 'autocomplete'
```

with `mode: 'combobox'` as the default, `'autocomplete'` in the `Omit<…>` list
dropped, and an `isAutocomplete` computed replacing the eleven `props.autocomplete`
reads. One of those reads is not a rename but a fix in its own right:

```diff
-const rootProps = useForwardProps(props.autocomplete ? reactiveOmit(rootPropsPick, …) : rootPropsPick, emits)
+const rootPropsOmitted = reactiveOmit(rootPropsPick, …)
+const rootProps = useForwardProps(computed(() => isAutocomplete.value ? rootPropsOmitted : rootPropsPick), emits)
```

The old line evaluates `props.autocomplete` once, at setup, so switching modes
after mount kept whichever prop set was chosen then. Wrapping it in a `computed`
makes it reactive.

## b24ui port

Applies verbatim to the component. `InputMenu.vue` had the identical pre-image
line for line — same `Omit<InputHTMLAttributes, 'autocomplete' | …>`, same
non-reactive `rootProps`, same eleven `props.autocomplete` reads — so every hunk
landed as written. The only rewrites are the fork's standing ones: `b24ui`
for `ui` in the slot classes, and `<Component :is>` against `@bitrix24/b24icons-vue`
where upstream renders `<UIcon :name>` (§1).

Deliberately narrower than upstream in three places, two of which are right:

- **Test names kept.** Upstream renamed its cases (`with autocomplete` → `with
  autocomplete mode`), which renames the snapshot keys and is what moves 46 lines
  in each of its two snapshot files. We renamed only the *props* the cases pass,
  so the keys stay put and the snapshots do not move — `081a9799`'s "snapshots
  unchanged — render is identical" is accurate, and the reason it is true is that
  the render genuinely does not change; only the prop spelling does.
- **Example file not renamed.** Upstream renamed
  `InputMenuAutocompleteExample.vue` → `InputMenuModeExample.vue`. We changed its
  contents (`autocomplete` → `mode="autocomplete"`) and kept the name, which
  keeps `name: 'input-menu-autocomplete-example'` in the docs page valid. Still
  the current state: the file is `InputMenuAutocompleteExample.vue` on `main`.
- **Playground line dropped — a real gap, closed later.** Upstream added
  `<UInputMenu placeholder="Autocomplete" mode="autocomplete" … />` to
  `playgrounds/nuxt/app/pages/components/input-menu.vue`. Nothing equivalent was
  added here, and when this log was first written neither `playgrounds/nuxt` nor
  `playgrounds/demo` had an autocomplete-mode row for InputMenu — small, but the
  only place the mode could be exercised by hand, and recorded nowhere until this
  backfill turned it up. **Fixed on 2026-08-31 (#520):** both playgrounds now
  carry the row, backed by its own `valueAutocomplete` ref, because in this mode
  `modelValue` is the input text rather than a selected item.

The native-attribute half of the change was ported and covered:

```ts
test('forwards the native autocomplete attribute to the input', () => {
  const wrapper = mount(InputMenu, { props: { items: […] }, attrs: { autocomplete: 'email' } })
  expect(wrapper.find('input').attributes('autocomplete')).toBe('email')
})
```

which is our own test, not upstream's — upstream covered the same behaviour with
a snapshot. It is still in `test/components/InputMenu.spec.ts` today.

Other `autocomplete` occurrences in the tree (`Select`, `SelectMenu`, `Input`,
`Editor`, `html.ts`) are the native HTML attribute and were correctly left alone.
