# Port: feat(CheckboxGroup/RadioGroup): support `icon` in items

**Upstream:** `07f3fe8dacbc00a2e9d7ff111068a438db7fabe2` (nuxt/ui, #6726)
**Decision:** port — the feature and the a11y fix it exposes; upstream's palette
refresh declined by maintainer decision

## Upstream change

21 files under one title, doing three separable things.

1. **The feature.** An item may carry an `icon`. On a checkbox it replaces the
   check mark; when `indicator` is `hidden` — which makes the control `sr-only` —
   it renders above the label instead, in both Checkbox and RadioGroup. A radio
   has no icon inside its indicator, so there the icon only ever appears in the
   hidden case.
2. **What the feature needs to look right.** The wrapper becomes a centred
   column (`flex flex-col items-center gap-1`), `container` stops holding the
   control's height open (`h-auto`), the icon gains explicit sizes because it is
   no longer always filling the indicator box, and `CheckboxIndicator` is dropped
   from the tree entirely when hidden rather than merely made invisible.
3. **A focus/hover/checked-colour refresh.** New `focusControl`/`focusCard`
   helpers, `hover:not-has-disabled:…` states, `has-data-[state=checked]:bg-${color}/10`,
   a `highlight: false` branch, and `outline-${color}/25 focus-visible:ring-${color}`
   moved off `base`.

## What was taken

**(1) and (2) in full.** The maintainer's decision was "feature plus the focus
fix, not the palette".

Adapting (1) was larger here than the diff suggests, because **this fork's
`Checkbox` had no `icon` prop at all**: the check and minus glyphs came straight
from `dictionary/icons` (`icons.check`, `icons.minus`), fixed. So the port adds
public API rather than extending it —

- `CheckboxProps.icon?: IconComponent`, defaulting to `icons.check`, used for the
  checked glyph and, when the indicator is hidden, above the label.
- `CheckboxGroupItem.icon` and `RadioGroupItem.icon`, plus a group-level `icon`
  on `CheckboxGroupProps` (upstream picks it from `CheckboxProps`; we now do the
  same). The item's own icon wins: `:icon="item.icon ?? props.icon"`.
- `RadioGroup`'s `icon` slot, which did not exist, and the matching entry in the
  item's `b24ui` pick.

`indeterminateIcon` is deliberately **not** added. Upstream already had one; here
the minus glyph stays governed by the icon dictionary, which is this fork's
override mechanism for it, and the feature does not need it.

Icons are components here, not iconify strings, so `@IconifyIcon` becomes
`@IconComponent` and `IconProps['name']` becomes `IconComponent` throughout.

## The focus fix, and why it is not just styling

With `indicator: hidden` the control carries `sr-only`, which in this fork
computes to `clip-path: inset(50%)`. The focus ring lived on that same element:

```
base: '… focus-visible:outline-(--b24ui-border-color) outline-transparent focus-visible:outline-2 …'
```

so tabbing to the checkbox produced a ring on an element clipped out of
existence — no visible focus indication at all. Upstream's fix is to move the
ring onto the element the reader can see. Their `focusCard()` helper is written
in their colour tokens; the mechanism, `:has(:focus-visible)` on the wrapper, is
what transfers. Expressed in this fork's idiom it is one class list per
component, reusing the same variables the control already used:

- `Checkbox` → on `root`: `outline-transparent has-focus-visible:outline-2 has-focus-visible:outline-offset-2 has-focus-visible:outline-(--b24ui-border-color)`
- `RadioGroup` → on `item`, with `--b24ui-background`, which the colour variant
  defines on `root` and CSS inheritance carries down.

Scoped to `indicator: 'hidden'` only. Upstream also moved focus for `variant:
card` generally; there our control is still visible and its own ring still works,
so that part is theirs to make, not a defect to fix.

## What was declined

**(3), the palette refresh.** `has-data-[state=checked]:bg-${color}/10`,
`${hover}border-accented`, `border-${color}/50`, the `highlight: false` branch and
the `focusControl` rewrite are all expressed in upstream's colour scale. This
fork colours these components with `style-filled*` classes and air tokens and
already has its own checked/hover treatment for `card` and `table`. Translating
them would be a design change wearing a port's clothes. Declined by decision.

Two consequences worth recording: upstream's two `'with highlight indicator
hidden'` render cases are not ported (they exercise a compound that does not
exist here), and their `icon` sizes for the *visible* indicator (`size-2.5` …
`size-4.5`) are not taken either — our `icon` keeps `size-full` inside the
indicator box, so nothing about the existing checkbox moves, and the explicit
sizes apply only in the hidden case.

## Docs and playgrounds

Upstream's docs diff also carries editorial rewrites of example copy
("This is the first option." → "Matches your device settings.") unrelated to the
feature; not taken.

Taken: the item-type bullet (`icon?: IconComponent`, linked to `#indicator`), the
`icon` entry in RadioGroup's item `b24ui` list, and the note under **Indicator**
on all three pages. The note is taken **without** upstream's
`:badge{label="Soon"}` — that badge tracks their release train, and `aa5f4af0`,
two commits later in this same queue, deletes it.

Per-item icons cannot be demonstrated through `::component-code` here: that
renderer casts a single named icon via `cast:`, and this fork's idiom for items
carrying components is a `.vue` example. So `checkbox-group.md` and
`radio-group.md` get `CheckboxGroupIconExample.vue` / `RadioGroupIconExample.vue`
(System/Light/Dark, `indicator: hidden`, `variant: table`), while `checkbox.md`
keeps the inline form with `cast: icon: 'RocketIcon'` and gains an `indicator`
selector so `start`/`end` stay reachable from the same block.

Both playgrounds, per the §6 checklist: `playgrounds/nuxt` **and**
`playgrounds/demo` each gain an icon row on `checkbox-group` and `radio-group`.
`MonitorIcon` does not exist in `@bitrix24/b24icons-vue`; `ThemeIcon` is the
outline set's equivalent and is what the examples use.

## Verify

The focus fix is measured, not asserted. Driving the built docs page in Chromium,
focusing the `sr-only` control and reading computed styles off the item:

| | outline on the item |
| --- | --- |
| classes removed (the state before this port) | `none 0px` |
| as shipped | `solid 2px rgb(0, 117, 255)` |

and the control itself computes `clip-path: inset(50%)`, which is why its own
ring was never a substitute. All four generated rules are in the stylesheet with
real declarations (`outline-width`, `outline-offset`, and both colour variants).

Across the three prerendered pages the icon renders inside the wrapper (3 + 3 + 1
occurrences), the wrapper is the centred column, and `container` carries
`h-auto`. Snapshot churn on `Table` is one `<!--v-if-->` placeholder per
selection checkbox, from the new `v-if` in the wrapper.

30 new tests, 12 new render cases. Gauntlet (`CI=true`): `dev:prepare` · `lint` ·
`typecheck` · `test` (6900 passed, 6 skipped) · `build` · `docs:generate`
(1261 routes, up from 1259 for the two new examples).
