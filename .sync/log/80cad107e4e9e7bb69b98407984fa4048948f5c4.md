# No-op: feat(locale): add Austrian language

**Upstream:** `80cad107e4e9e7bb69b98407984fa4048948f5c4` (nuxt/ui, #6806)
**Decision:** no-op — outside this fork's locale contract, and it carries no
translations

## Upstream change
A new `src/runtime/locale/de_at.ts` plus one export line in
`src/runtime/locale/index.ts`. The whole file:

```ts
import type { Messages } from '../types/locale'
import { defineLocale } from '../composables/defineLocale'
import de from './de'

export default defineLocale<Messages>({
  name: 'Deutsch (Österreich)',
  code: 'de-AT',
  messages: de.messages
})
```

Note `messages: de.messages` — it is an alias. Unlike its sibling `de_ch.ts`,
which spells out Swiss spellings (`Schliessen` for `Schließen`, and so on), this
file ships **zero** Austrian-specific strings. It registers a name and a BCP-47
tag; the content is German German, byte for byte.

## Why it does not apply

**1. It would add nothing.** Ported here it would be a registry entry whose
messages are identical to `de`'s. Nothing renders differently.

**2. This fork's locale registry is the Bitrix24 portal language set, not a
BCP-47 space.** All 20 codes are two-letter Bitrix24 identifiers — `in`, `kz`,
`ua`, `vn`, `sc`, `tc`, `br`, `la` — and there is not a single region-tagged
code among them:

```
$ grep -n "code: '" src/runtime/locale/*.ts | grep -E "code: '[a-z]{2}-"
(no BCP-47 style codes — all two-letter Bitrix24 codes)
```

Regional variants already exist in this set and are still expressed as
Bitrix24 codes: `br` is *Português (Brasil)*, `la` is Latin-American *Español*.
`de-AT` is not a Bitrix24 portal language, so it would be the one entry in the
registry that no Bitrix24 portal can be set to — see `e333e8d`, where the same
reasoning kept `ua`/`kz`/`vn` from being "corrected" to ISO codes.

**3. The fork already ships the supported path for this, and it is better.**
`extendLocale` is implemented in `src/runtime/composables/defineLocale.ts`,
exported from `composables/index.ts`, auto-imported via `src/imports.ts`, and
documented at `/docs/composables/extend-locale/`. The i18n integration pages
even use `de-AT` as their worked example of a region tag. A consumer who wants
Austrian German writes:

```ts
const locale = extendLocale(de, {
  locale: 'de-AT',
  messages: { /* actual Austrian vocabulary */ }
})
```

which is strictly more than upstream's file offers, since it can carry the
vocabulary that makes the variant worth having.

## Observed, left alone
`LocaleSelect.vue`'s flag lookup comments `la: 'es', // Catalan -> Spain`, but
`la.ts` is `Español` (Bitrix24's Latin-American Spanish); Catalan would be `ca`.
A stale comment in the same family as the ones corrected in `e333e8d`, but not
in this commit's scope — noted for whoever touches that table next.

Nothing changed. Suite unaffected.
