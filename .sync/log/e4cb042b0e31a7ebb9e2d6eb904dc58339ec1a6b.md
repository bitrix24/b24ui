## Upstream change

`truncateHTMLFromStart` walked the HTML backwards by UTF-16 code unit, so a
truncation boundary landing between an astral character's surrogates emitted an
unpaired half that renders as `�`. Two hunks: convert to `Array.from(html)` and
iterate code points, and measure the budget in code points too
(`Array.from(content.slice(markIndex)).length`), so the two sides stay in the
same units. Plus 37 lines of test.

## Why this is a no-op here

Not "similar" — **our file already contains upstream's post-image verbatim**,
including the four-line comment about astral characters and `<`/`>` being single
code units, which is byte-identical. Both hunks are present:
`const chars = Array.from(html)` at `search.ts:163`, and the budget line at
`search.ts:358`, differing only by this fork's third argument.

The same holds for the tests. Upstream's new `describe('truncation from the
start')`, its `LONE_SURROGATE` regex and its `highlightAfterFiller` helper are
all already in `test/utils/search.spec.ts` — the block was added here in #405 and
is named in PORTING.md's 2026-08-15 entry.

The fork is ahead rather than level, on the same lines:

- **Grapheme snapping.** A code point is still not what a reader sees, so the cut
  is snapped past any grapheme cluster it lands inside (`createClusterSnapper`).
  Upstream stops at the code point and will still cut a flag in half.
- **No quadratic prepend.** Upstream rebuilds `truncated = char + truncated` per
  character; ours counts retained code units and slices once, which is also what
  leaves an index for the snapper to move.
- **A stronger assertion.** Upstream's astral test only scans for lone
  surrogates. Ours counts how many astral characters *survived*, explicitly
  because an implementation that deletes every one of them emits no lone
  surrogate either and would pass a test named "never splits an astral
  character".

Verified by running the suite rather than by reading: `test/utils/search.spec.ts`
is 148 green on the pre-image, unchanged.
