# port — nuxt/ui@584016bdec75b1eb799d30ec95eb85ed3b49d38b

**Upstream:** fix(module): use `@custom-variant` for `light` and `dark` variants (#7023)

**Decision:** port, extended to every variant defined the same way.

## What it changes, measured

`src/runtime/index.css` defined its variants with a top-level, body-less
`@variant name (selector);`. Tailwind's documented form for *defining* a
variant is `@custom-variant`; `@variant` is the directive for *applying* one
inside a rule.

The old form was not broken on the Tailwind this fork builds with. In
`tailwindcss@4.3.3`'s `dist/lib.js`, a top-level `@variant` with no body is
renamed to `@custom-variant` before anything else sees it — a compatibility
shim. Checked twice rather than inferred:

- compiling both spellings of `dark` and `edge-dark` directly gives the same two
  rules and no warning;
- compiling the **real** `src/runtime/index.css` from `main` and from this
  branch, with every one of its variants used (`light`, `dark`, `edge-dark`,
  `edge-light`, `bitrix-mobile`, `bitrix-desktop`, `web` — each `:flex` and
  `:hover:underline`), gives **byte-identical** output, 284,253 bytes both, and
  every variant produces its rule, so the comparison is not over nothing.

So this moves the file onto the documented form and off a shim a later Tailwind
may drop; it changes no output today.

## b24ui adaptation

Upstream defines two variants and changed two lines. This fork defines seven —
`light`, `dark`, plus its own `edge-dark`, `edge-light`, `bitrix-mobile`,
`bitrix-desktop` and `web` — all in the same form in the same file. All seven
are converted; changing only upstream's two would leave the file half on the
shim. No other top-level `@variant` exists in `src/`, `docs/app` or the
playgrounds.
