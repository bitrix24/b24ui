## Not only versions

Renovate's title says dependencies, and the commit carries a **runtime fix** that
only exists because of one of them:

```diff
+import { toRaw } from 'vue'
-export function validateSchema<T extends object>(state: T, schema: FormSchema<T>) {
+export function validateSchema<T extends object>(state: T, _schema: FormSchema<T>) {
+  const schema = toRaw(_schema)
```

Zod 4.5 resolves `~standard` through a lazy getter that captures `this`. When the
schema is held in reactive state it arrives as a Vue proxy, so the getter reads
the non-configurable `_zod` internals *through the proxy*, which violates the
proxy invariant and throws. `toRaw` unwraps it before any of the shape checks run.

**Ported verbatim**, comment included. Our `validateSchema` had the identical
pre-image at `form.ts:80`. Worth stating plainly: this fork is on `zod ^4.4.3`,
so the bug does not bite here **yet** — it becomes live with the `^4.5.4` bump in
the same commit, which is also taken. The fix is not speculative; it arrives with
its trigger.

## `pnpm-workspace.yaml`: one removal taken, one refused

Upstream deletes both its `@nuxt/content>@nuxtjs/mdc` override and its whole
`minimumReleaseAgeExclude` block. These were decided separately and by
measurement, not by following.

**`minimumReleaseAgeExclude` — removed.** Ours held one entry,
`@nuxtjs/mdc@0.23.1`, added when that release was younger than the policy's
minimum age. Verified rather than assumed: with the block gone,
`pnpm install` still reports *"Lockfile passes supply-chain policies (1794
entries)"*. The release is simply old enough now. Dropping a spent exception
tightens the policy; nothing here weakens it.

**`@nuxt/content>@nuxtjs/mdc` — kept.** Upstream could drop it because it moved to
`@nuxt/content` 3.16.0, whose declared cap is `^0.23.1` rather than 3.15's
`^0.22.2`. That reasoning is about upstream's tree, so it was tested against ours:
remove the override, reinstall, read `pnpm-lock.yaml` — and **two** mdc versions
appear, `0.22.2` alongside `0.23.1`, which is precisely the failure the override's
comment describes (two copies mean component-meta reads different components than
the module registers). Restore it and the lockfile is back to a single `0.23.1`.

The copy that pulls the old mdc is the **root peer** `@nuxt/content: ^3.0.0` —
deliberately wide so consumers are not forced onto one content minor — which this
lockfile resolves to 3.14.0. `docs`, `playgrounds/nuxt` and `playgrounds/demo` are
all on 3.16.0 and are not the cause; levelling `playgrounds/demo` was tried first
and changed nothing. A full lockfile regeneration might lift that peer and let the
override go, but that is a larger change than a dependency port should make on its
own, so the override stays with its comment rewritten to say all of this.

**A note on method, because the first attempt got it wrong.** `find
node_modules/.pnpm` was used to count copies, and it lies: the store keeps
directories from earlier installs, so a version that is no longer resolved still
appears, and after restoring the override it showed `0.22.2` that the lockfile did
not contain. The conclusion above was re-derived from `pnpm-lock.yaml`, which is
the resolution. Anyone re-checking this should read the lockfile, not the store.
