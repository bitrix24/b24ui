# port — nuxt/ui@619c7328106736bf799d70c4fc628f1378f5185d

**Upstream:** fix(InputMenu): round corners inside a FieldGroup in multiple mode
(#6968)

**Decision:** port — the fork has the same `root`/`base` collapse in `multiple`
mode and the same `defuFn` inheritance from `input`, so the defect is present
verbatim.

## The defect

`InputMenu` inherits its `fieldGroup` variant from `input`, whose rounding is
written as `group-not-only:group-first:rounded-e-none` etc. Those utilities need
a **separate ancestor** carrying `group` — in `input` that is the `root` wrapper
around the `<input>`.

In `multiple` mode `InputMenu` renders `ComboboxRoot` with `as-child` and
`Component.Anchor` renders the element, so `root` and `base` are **the same
DOM node**. A `group-*` variant has no ancestor left to match against, and the
rounding silently does nothing: an `InputMenu multiple` inside a `B24FieldGroup`
kept its full border radius on both sides.

Measured rather than assumed — the same probe, before and after:

```
before:  group-not-only:group-first:rounded-e-none
         group-not-only:group-last:rounded-s-none      <- never matches
after:   group-[.is-field-group]/items:not-only:first:rounded-e-none
         group-[.is-field-group]/items:not-only:last:rounded-s-none
```

## The fix

Structurally 1:1 with upstream:

- `variants.fieldGroup.{horizontal,vertical}` keep **only** the `group` marker
  from `fieldGroupVariantWithRoot…root`, written **as functions** — `defuFn`
  replaces a value produced by a function instead of merging it, which is what
  drops `input`'s inherited `base` rounding rather than stacking on top of it.
- four `compoundVariants` pick the right set: `multiple: false` gets
  `fieldGroupVariantWithRoot.fieldGroup.*.base` (the `group-*` form, correct when
  `root` really is a separate wrapper), `multiple: true` gets
  `fieldGroupVariant.fieldGroup.*` (the self-positional form).

## b24ui adaptation

Upstream's `fieldGroupVariant.fieldGroup.horizontal` uses bare
`not-only:last:rounded-s-none`. **The fork's is scoped to a named group** —
`group-[.is-field-group]/items:not-only:last:rounded-s-none` — because
`B24FieldGroup` marks its wrapper `group/items is-field-group`. The theme change
is therefore identical while the class strings are not, so the ported test
asserts what the fork actually emits, read off the rendered DOM rather than
copied from upstream.

Also: the fork's theme factory takes no `options` argument and its
`compoundVariants` are grouped in `// region … ////` blocks, so the four entries
go in their own region at the head of the array.

## Coverage

Both directions are pinned, and each load-bearing part of the theme was mutated
separately rather than testing the change as one lump:

| mutation | caught by |
| --- | --- |
| remove `variants.fieldGroup` | `with multiple rounds its corners inside a FieldGroup` |
| `() => ({ … })` → `{ … }` (defuFn merges instead of replacing) | same test |
| remove the two `multiple: true` compoundVariants | same test |
| remove the two `multiple: false` compoundVariants | `without multiple rounds its corners inside a FieldGroup` |

The first two are caught only because the multiple-mode test also asserts
`.not.toContain('group-not-only:group-last:rounded-s-none')`. **Upstream's test
has no such assertion**, and with a positive-only assertion both mutations stayed
green: the dead class merges back in beside the working one and `toContain` still
passes. The negative assertion is a fork addition for that reason.

The single-mode test is a fork addition too — without it, deleting the
`multiple: false` compoundVariants is a silent regression, because the function
form has already thrown away what `input` would have supplied.
