# No-op: docs(icons): document what `clientBundle.scan` covers

## Upstream change

Two files, +40 lines: `6.integrations/1.icons/1.nuxt.md` and `2.vue.md` gain a
paragraph explaining the limits of `@nuxt/icon`'s client bundle scanner —

- it reads only `.vue`, `.jsx`, `.tsx`, `.md`, `.mdc`, `.mdx`, `.yml`, `.yaml`;
- it matches icon names only as **literal strings**, so a list of links in a
  `.ts` file is missed, as is anything built like `` `i-lucide-${name}` ``;
- `clientBundle.scan.globInclude` widens the file list, replacing the default;
- names known at build time can go in `clientBundle.icons`; names that exist only
  at runtime cannot be bundled and are fetched from `/api/_nuxt_icon` (SSR) or
  the Iconify API.

## b24ui

**Nothing here to document, because none of that machinery exists.** Checked
rather than assumed:

- Our icons are `@bitrix24/b24icons` — Vue **components**, imported by name and
  bundled by the compiler. There is no string-literal icon name to scan for, so
  the whole failure mode the paragraph warns about — a name the scanner cannot
  see — cannot arise.
- `clientBundle`, `globInclude` and `/api/_nuxt_icon` appear nowhere in `docs/`
  or `src/`.
- `@nuxt/icon` survives in exactly two places, neither of them a dependency: a
  commented-out block at `src/module.ts:139`, and prose inside an unrelated
  Accordion example.
- Both of our icons pages document `@bitrix24/b24icons` and its 1,400+ icons,
  and say setup is automatic — there is no scanner to configure.
