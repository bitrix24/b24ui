# port — nuxt/ui@b0e1d715ce1d87b3ea00456e3cc655ae8b29dec7

**Upstream:** refactor(unplugin): resolve vue runtime paths from runtimeDir (#6960)

**Decision:** port — the same pattern is here in the same files, and the reason
transfers whole.

## Upstream change

Four `resolvePathSync` calls in the Vue build adapter stop resolving relative to
`import.meta.url` and resolve an absolute path anchored on `runtimeDir` instead:

```diff
-resolvePathSync('../runtime/vue/plugins/router', { extensions: […], url: import.meta.url })
+resolvePathSync(join(runtimeDir, 'vue/plugins/router'), { extensions: […] })
```

The reason is the `AGENTS.md` line added in the same commit: **from the published
build, only the two entry files may resolve paths from `import.meta.url`, because
bundled files can land in any output chunk.** `../runtime/…` is only correct while
the file sits where the source tree put it; after bundling it is a guess.

## What changed here

The same four sites, with this fork's names — `src/plugins/plugins.ts` (router,
head, color-mode) and `src/plugins/bitrix24-environment.ts` (the router-mode
stub). Upstream also converts an `icons` plugin; this fork has none, because
icons come from `@bitrix24/b24icons-*`.

After the change, a grep for `import.meta.url` under `src/` outside the two entry
files returns only `src/templates.ts:96-97`.

## The rule has a live exception, on both sides

`src/templates.ts` resolves `./theme/…` and `./utils/theme` from
`import.meta.url`, which is exactly what the new rule forbids. Upstream added the
rule **without** changing those lines, and they are still there at `v4` HEAD.

Ported faithfully rather than fixed: tightening a rule further than upstream did
would diverge the file for no measured reason, and the lines may be deliberate —
`templates.ts` runs at build time in both adapters, not from the published
runtime. The exception is written into the `AGENTS.md` bullet so the rule does not
read as absolute when the tree contradicts it.

## Evidence

**The build is not the evidence.** The vue adapter built before this change and
after it, so a green `dev:vue:build` says nothing about which code path ran.

**The mutation is.** Pointing one site at a name that does not exist —
`join(runtimeDir, 'vue/plugins/router-NOPE')` — fails `dev:vue:build` with:

```
Error: Cannot find module /home/user/b24ui/dist/runtime/vue/plugins/router-NOPE
```

That proves two things at once: the line is live and resolved at build time, and
the path it produces is absolute **under `dist/runtime`** — anchored on the
runtime directory rather than on wherever the bundler placed the chunk, which is
the whole point of the commit.

## Note for the next port

This is the first of a two-step change. `b6cb8972`, two commits later, replaces
the absolute path with a `file://` URL because `resolvePathSync` parses an
absolute Windows path like `D:/…` as a `d:` URL scheme. `d00e9dee` sits between
them, so §6 step 4b forbids batching the two — they land in upstream's order, and
this fork carries that Windows defect between the two merges. No release is cut
in between.
