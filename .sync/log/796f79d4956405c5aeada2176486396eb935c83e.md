# port — nuxt/ui@796f79d4956405c5aeada2176486396eb935c83e

**Upstream:** fix(Toaster): prevent `onClick` from being called twice (#6980)

**Decision:** port — the defect is present here verbatim, and the line to change
is byte-identical to upstream's pre-image.

## The defect

`Toaster` renders each toast with

```
v-bind="omit(toast, ['id', 'close', '_duplicate', '_updated'])"
…
@click="toast.onClick && toast.onClick(toast)"
```

on **the same element**. So `onClick` arrived twice: once spread in as a
fallthrough listener by `v-bind`, once as the explicit handler. Both fired on a
single click.

Both sides are structurally identical here — `Toaster.vue:138` matches upstream's
pre-image exactly, `useToast.ts` declares the same
`onClick?: (toast: Toast) => void`, and neither `Toast.vue` handles the prop in
its template.

Reproduced before fixing rather than reasoned about: a probe adding a toast with
a spy and clicking it reported **2 calls for one click**.

## The fix

`'onClick'` added to the omit list. One line, identical to upstream.

## b24ui adaptation — the test needed one, the fix did not

Upstream's test transfers in substance, and its `[data-slot="base"]` selector
works here, which was checked rather than assumed: the probe found
`[data-slot="base"]` present and `[data-slot="root"]` absent on the rendered
toast, so `Toaster`'s caller-supplied marker wins over `Toast`'s own.

Worth noting because it looks like it contradicts #619: there, a caller's
`data-slot` was **lost** on `Button`. The mechanism is different. In `Button` the
caller's attributes arrive inside the template through `slotProps`, which was
bound before the static `data-slot="base"`, so the static value overwrote them.
Here they arrive by ordinary Vue fallthrough, which is merged last and therefore
wins. Same symptom to look for, opposite outcome, and only a probe distinguishes
them.

What did need adapting is **where the toast API is obtained**. Upstream calls
`useToast()` in the test body. `useToast` calls `inject()`, and outside a
component instance Vue warns — this fork has a console gate that fails any spec
logging while rendering, and `useToast.spec.ts` is in its `KNOWN_NOISY_SPECS` for
exactly this warning. Adding `Toast.spec.ts` to that list is what the gate itself
calls a last resort, so the test takes the API from inside a small harness
component's `setup()` instead. No warning, no exemption.

| revert the omit fix | red — `expected "vi.fn()" to be called 1 times, but got 2 times`, the defect exactly |

The second is worth keeping. With only the fallthrough listener the handler is
still called once, so a test asserting the count alone would stay green — it is
the `toHaveBeenCalledWith(objectContaining({ id, title }))` half that catches it,
because a fallthrough listener receives the `MouseEvent` rather than the toast.
So the test pins *which* of the two paths survives, not merely that one does.
