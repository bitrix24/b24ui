# Port: fix(theme): unify motion easing and respect prefers-reduced-motion

**Upstream:** `735b264e4df8565d05cd522df36406df35fe5896` (nuxt/ui)
**Decision:** port — adapted (one hunk deliberately skipped)

## Upstream change
Theme-wide motion pass across 36 theme files, `keyframes.css` and ~100
snapshots:
1. **Easing unified by animation type** — not a blanket swap:
   presence/state animations (`scale-*`, `slide-*`, `fade-*`, `collapsible-*`,
   `accordion-*`, `toast-*`) → `var(--ease-out)`; continuous travel loops
   (`carousel*`) → `linear`; oscillating loops (`swing`, `elastic`) →
   `var(--ease-in-out)`. Inside `animate-[…]` the bare `ease-out` keyword is
   CSS's `cubic-bezier(0,0,.58,1)`, while the `ease-out` *utility* maps to
   Tailwind's `--ease-out` — the two never matched, which is what "unify" fixes.
2. **`@media (prefers-reduced-motion: reduce)` in `keyframes.css`** redefining
   26 presence keyframes to fade-only, covering every component that references
   them in one place.
3. **Selective transition hardening** — explicit `ease-out` plus
   `motion-reduce:transition-none` on movement transitions.
4. `elastic` / `elastic-vertical` keyframes reworked from `margin-left`/
   `margin-top` to `left`/`top` (and 90% → 100%).

## b24ui port
- **`src/runtime/keyframes.css`** — appended the reduced-motion block verbatim.
  All 26 keyframes upstream redefines exist in b24ui, so it maps 1:1.
  **This has more effect here than upstream:** b24ui's earlier reduced-motion
  pass (PR #279) gated only decorative loops with `motion-safe:` — **77**
  `animate-[…]` usages (modal, toaster, dropdown-menu, collapsible, chat-tool,
  …) were still ungated. The keyframe redefinitions cover exactly those, and
  compose cleanly with the existing `motion-safe:` classes (those stay fully
  disabled; the rest degrade to a fade).
- **Theme files (19)** — rewrote **70** `animate-[…]` easings by the upstream
  rule: 54 → `var(--ease-out)`, 10 → `linear` (carousel family, shimmer,
  progressbar-loading), 6 → `var(--ease-in-out)` (swing/elastic family).
- **`progress.ts` / `toaster.ts`** — the same three transition edits upstream
  made, on slots b24ui has identically: `indicator` and `toaster.base` gain
  `motion-reduce:transition-none`, `status` gains `ease-out` +
  `motion-reduce:transition-none`, `step` gains `ease-out`.

### Skipped — `elastic` keyframes rework
Not ported. Upstream moves the animation from `margin-left`/`margin-top` to
`left`/`top`, which only works on a positioned element. b24ui's Progress
`indicator` is `size-full` and **statically positioned** inside a `relative
overflow-hidden` base, so `left`/`top` would silently stop it moving — the bar
would only pulse in width. (b24ui's other consumer, `table.thead::after`, is
`after:absolute` and would be fine.) The current margin-based keyframes work
for both consumers, and the change is cosmetic (90% → 100% travel), so the risk
isn't worth it. Worth revisiting together with a deliberate decision about
positioning the Progress indicator.

### Not ported — the wider transition sweep
Upstream also touches transitions in other theme files. Those edits are
per-slot and file-specific, and b24ui's slot contents diverge substantially, so
a blanket `motion-reduce:transition-none` across b24ui's 80 `transition-*`
usages would go beyond what upstream did (reduced motion targets movement, not
colour/opacity). Only the slots with a verified 1:1 upstream counterpart were
changed. A dedicated pass over b24ui's remaining movement transitions is a
sensible follow-up.
