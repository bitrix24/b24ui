# Port: docs(mcp): compact component metadata and rank search by intent

**Upstream:** `4fdccd333b8a0c6956e1c245cfddf781f13c81a0` (nuxt/ui, #6829)
**Decision:** port — largest commit in the queue (57 files); one half deliberately not replayed

## Upstream change

Three things at once, all in service of the MCP server:

1. **`keywords:` frontmatter** on 42 component pages, plus `keywords` and the
   missing `content` category in the docs collection schema. Keywords are
   alternate names from other ecosystems — `segmented control` for FieldGroup,
   `combobox` for InputMenu, `dialog` for Modal.
2. **`docs/server/utils/searchComponents.ts`** (new) — `scoreComponent`, a
   phrase-and-token ranking over name/title/keywords/description, replacing
   `search-components`' substring filter.
3. **`docs/server/utils/componentMeta.ts`** (new) — `compactProp`, which drops
   `vue-component-meta`'s recursive `schema` field (megabytes on generic props)
   and resolves the same defaults the docs app resolves; plus the
   `linkKeys`-derived partition that splits a Button-like component's props from
   the ones it inherits from Link. `src/runtime/utils/link-keys.ts` is split out
   of `link.ts` so the docs server can import the list without dragging in
   `@vueuse/core` and `ohash`.

`transformMDC.ts` routes `component-props` through `compactProp` and groups the
inherited half under a comment. `get-component-metadata` gains a `full` flag;
the `implement-component-with-props` prompt stops rolling its own fetch.

## b24ui port

Ported in full except `skills/`, which §2 keeps b24-authored — upstream's four
skill/reference edits are prose about `nuxt-ui` and have no counterpart to
replay into.

**Frontmatter (39 of 42).** `carousel`, `slider` and `tree` have no page here.
The keyword lists are upstream's verbatim; they are ecosystem vocabulary, not
Nuxt-specific.

**Schema.** Adapted rather than copied. Upstream's diff adds `content` to the
`category` enum; auditing the enum against what the frontmatter actually writes
turned up three more values this fork has been using with no entry —
`deprecated` (`sidebar-layout`), `components` (the 15 typography pages) and
`integrations` (the i18n page). The value still reaches the collection at
runtime, so nothing ever failed; what was wrong is the declared contract and the
`category` union the MCP tools filter on. All four are declared now.

**`searchComponents.ts`.** Verbatim — no fork-specific names in it.

**`componentMeta.ts`.** Adapted: `B24` component-meta prefix, `../../.nuxt/b24ui`
theme path, and the `OWN_LINK_KEYS` jsDoc trimmed to `active`/`activeColor`
(Button here has no `activeVariant`). The 14 keys are unchanged, and they are
correct for this fork by derivation: our `LinkPropsKeys` union is the same 25
keys as upstream's, so the complement of our 38-entry `linkKeys` is the same 13,
plus `active`.

Carried one silent upstream fix with it: both forks' `get-component-metadata`
returned `emits: metadata.meta.emits`, and `vue-component-meta` emits `events`.
That key has been `undefined` in every MCP response since the tool was written.
`componentMeta.ts` reads `events`.

**`transformMDC.ts`.** Took the grouping and the `compactProp` routing, keeping
this fork's `propItemHandler` customisations (the `depth`/`activeDepth` removal
and the `air-*` colour ordering) — they operate on the type string, which
`compactProp` still produces. The inherited-group URL is built from
`config.public.canonicalUrl`/`baseUrl` rather than hardcoded, since this docs
site's base path is env-driven.

Two visible output changes, both intended by upstream: prop defaults now fall
back to the theme's `defaultVariants` (so `@default 'md'` and
`@default 'air-secondary-no-accent'` appear on Button where nothing did before),
and `@default` values are no longer double-quoted.

Verified on the generated site: `button.md` is the only page that gets the split
(`hasLinkPassthrough` wants both `to` and `href`; `link.md` is excluded by name),
which matches upstream.

**`1.mcp.md`.** N/A — this fork has no MCP documentation page. `7.ai/` holds only
`llms-txt` and `skills`.

## Tests

Two new specs, each mutation-tested rather than assumed.

`test/utils/search-components.spec.ts` — the search tool's description makes
three concrete promises (`"segmented control" finds FieldGroup` and two more)
about `keywords:` frontmatter in unrelated files. The spec parses the promises
out of the tool source and re-runs the real ranking against the real frontmatter,
so deleting a keyword breaks the claim instead of quietly changing the answer.
It also holds the `category` enum to the values in use — the defect above — and
asserts the tool still selects `keywords`, without which the ranking degrades to
name-and-description with no error.

What it deliberately does not assert: that a keyword's own component ranks first.
Keywords are legitimately shared (`disclosure` is both Accordion's and
Collapsible's, `combobox` both InputMenu's and SelectMenu's) and the winner is
decided by an alphabetical tiebreak. Pinning that would encode an accident.

Mutations tried, each red: drop `combobox` from `input-menu.md`; drop `keywords`
from the tool's `.select()`; drop `components` from the enum; add a keyword below
the 3-character token floor; break the hand-rolled frontmatter reader.

`test/utils/link-passthrough.spec.ts` — `OWN_LINK_KEYS` is derived from two files
that do not import it. Adding a key to `LinkPropsKeys` moves a prop between the
docs groups with nothing to say so. The spec recomputes the derivation from
`linkKeys` and `Link.vue`. Mutations tried, each red: add `as` to
`LinkPropsKeys`; typo `viewTransition`; drop `disabled` from `linkKeys`; drop the
`linkKeys` re-export from `link.ts`.

`componentMeta.ts` is read as text there rather than imported — it pulls in
`docs/.nuxt/b24ui`, which only exists once the docs app has been prepared.
