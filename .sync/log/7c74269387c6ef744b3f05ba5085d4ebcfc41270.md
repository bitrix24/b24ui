# Port: fix(components): resolve theme props consistently in form controls

**Upstream:** `7c74269387c6ef744b3f05ba5085d4ebcfc41270` (nuxt/ui, #6834)
**Decision:** port — the whole commit, plus one fork-specific defect it exposed

## Upstream change

`useFormField` returns `size`, `color`, `highlight` and `disabled` holding only
what the wrapping `<Form>` / `<FormField>` supplied. Reading one of them bare
therefore drops everything below it in the precedence chain — `<Theme :props>`
and `app.config`. The correct read is always `formFieldX.value ?? props.X`,
against the `useComponentProps` proxy.

That was done inconsistently. Most `tv()` calls had the fallback; almost no
template binding did, and a template binding is where it is invisible: a ref
auto-unwraps there, so `:disabled="disabled"` reads identically whether
`disabled` is the raw ref or a resolved computed. The result was controls that
were *painted* disabled by a theme without being disabled.

Two smaller fixes ride along:

- **Boolean props.** Vue auto-casts an unset Boolean prop to `false`, so
  `highlight` and `disabled` came back `false` rather than `undefined` and the
  `??` short-circuited before the proxy was read. `useFormField` now normalizes
  them back to `undefined`.
- **A debounce that outlives the component.** `emitFormInput`'s trailing call
  still fires after teardown, validating a field that is no longer rendered when
  the input unmounts inside the debounce window. Guarded with `onScopeDispose`.

And the part that makes it stick: a **new ESLint rule**,
`no-unresolved-form-field-refs`, that fails on any read of one of those refs
without a `?? props.X` fallback — in script *and*, more strictly, in template,
where any appearance at all is reported.

## b24ui port

Ported in full. The fork's `useFormField` had the identical shape, so the
composable changes applied verbatim; the ESLint rule needed only the plugin
namespace (`bitrix24-ui`) and the `B24*` component names in its messages.

**The rule is what drove the rest.** Rather than replay twenty diffs by hand,
the rule went in first and was allowed to find the sites: **69 violations across
19 files**. That list is not upstream's — this fork has `PageCardGroup` and
`Range`, which upstream does not, and `InputRating` names its ref `formDisabled`
rather than `disabled`. All 69 are fixed and the rule is now clean.

The shape is upstream's throughout: rename the destructured ref to
`formFieldX`, resolve it once into a `computed`, and read that computed
everywhere.

Two adaptations:

- **`inputSize` / `selectSize` keep their names.** Upstream renames its
  equivalent to `size`, shadowing the prop and needing a `vue/no-dupe-keys`
  disable. This fork already had a distinct name, which is clearer; the
  fallback moved into it (`fieldGroupSize.value ?? formFieldSize.value ??
  props.size`) and the `?? props.size` at the `tv()` site went away. Upstream's
  `||` → `??` change in that chain is taken as-is: with `||`, a falsy-but-valid
  size would fall through.
- **`InputRating`** resolves `formFieldDisabled.value ?? props.disabled` into
  `isDisabled`, keeping its existing `disabled` computed (which also folds in
  `readonly`) as the interaction flag. `readonly` blocks interaction but only an
  explicit `disabled` dims the control, and that distinction had to survive.

## The defect this exposed

Upstream's own test — `:props color on a checkbox group reaches its items` —
failed here, and not because of the port.

`CheckboxGroup` carried `withDefaults(..., { color: 'air-primary' })`. A
`withDefaults` default lands on the **raw** `_props`, which is what
`useFormField` receives, so `formFieldColor.value` was never `undefined` and
`formFieldColor.value ?? props.color` could never reach the proxy.
`<B24Theme :props>` was unreachable for that component's colour — before this
commit and after it.

The `withDefaults` default is removed. `src/theme/checkbox.ts` supplies the same
`air-primary` through `defaultVariants`, which is the layer the documented
precedence puts it in (`… > app.config > withDefaults > tv defaults`), so the
default rendering is unchanged — every existing snapshot passes untouched — and
the theme layer now reaches it.

It is the only form control in the fork with such a default; checked all of
`Checkbox`, `RadioGroup`, `Switch`, `Range`, `InputRating` and `Listbox`.

## Tests

`test/components/Theme.spec.ts` gains upstream's five cases, with the
assertions grounded in this fork's actual output rather than translated by eye —
each discriminator was read off a real render first:

- `:props highlight` swaps the checkbox ring from `ring-(--ui-color-base-5)` to
  `ring-(--b24ui-border-color)`;
- `:props disabled` on `FileUpload` produces `cursor-not-allowed`,
  `aria-disabled="true"` **and** `tabindex="-1"` — the last two are the part
  that a styling-only regression would miss;
- `<B24Form disabled>` still beats an explicit `:disabled="false"` from the theme;
- `:props color` on a `CheckboxGroup` reaches the items (`style-filled-success`);
- a `FormField` error still beats it there (`style-filled-alert`).

Mutations tried, each red: stop normalizing `highlight`/`disabled` to
`undefined` in `useFormField`; bind `FileUpload`'s raw `formFieldDisabled` in
the template again; give `CheckboxGroup` its `withDefaults` colour back.

The 69 lint violations are themselves a regression test — the rule is `error`,
so CI fails on any new unresolved read.
