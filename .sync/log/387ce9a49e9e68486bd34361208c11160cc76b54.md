# Port: feat(locale): validate locales against CLDR in CLI and tests

**Upstream:** `387ce9a49e9e68486bd34361208c11160cc76b54` (nuxt/ui, #6826)
**Decision:** port — the structural half only; the CLDR half is actively wrong here

## Upstream change
Five files. A new `test/locale.spec.ts` with eight per-locale checks, a
`vitest.config.ts` include for it, CLDR-derived defaults and validation in
`cli/commands/make/locale.mjs` (`--name` and `--dir` become optional; the code
is rejected unless CLDR knows it), and two docs edits following from that.

## Why the CLDR half cannot come across
b24ui's locale codes are **Bitrix24 portal language codes**, not ISO 639-1 —
the invariant already recorded for `e333e8d` (which is why `tj → tg` was not
mirrored) and `80cad10`. Ran every one of the fork's 20 codes through `Intl`
rather than reasoning about it:

| | codes |
|---|---|
| unknown to CLDR | `kz`, `tc`, `ua`, `vn` |
| **known, but a different language** | `br` → Breton (we mean *Português (Brasil)*), `la` → Latin (*Español*), `sc` → Sardinian (*中文（简体）*), `in` → deprecated Indonesian (*हिन्दी*) |
| correct | `ar de en fr id it ja ms pl ru th tr` |

So upstream's `has a code known to CLDR` would fail on four **and pass on four
more while asserting the wrong language** — worse than no check. `is named
after the CLDR own-language name` fails on all eight, since it looks the name
up *by* that code. `has the direction CLDR expects` would pass today, but only
by luck: unknown codes default to `ltr`, and every fork locale except `ar` is
`ltr`. A check that is right by coincidence is not a check.

`keeps the index exports sorted alphabetically` is also out: b24ui's
`src/runtime/locale/index.ts` is deliberately **grouped in threes under a
header comment**, not sorted. Verified: `sorted? False`.

## What was ported
`test/utils/locale.spec.ts` — six checks, all independent of the code being an
ISO tag:

- exports every locale file from the index under its filename;
- has a unique code per locale;
- has a code matching its filename;
- has a direction (`ltr`/`rtl`) — the fork-shaped remnant of upstream's CLDR
  direction check: it still catches a typo in an explicit `dir`, without
  claiming to know what CLDR thinks the direction should be;
- has the exact same message keys as `en`;
- has no empty message;
- **has the same placeholders as `en` in every message.**

That last one is the reason this commit was worth porting at all. A
placeholder whose casing or spelling drifts fails **silently** — no error, no
red test, just a literal `{Slide}` rendered to the user. That is exactly the
bug `10ec237` fixed upstream, and when it was processed here the fork was
cleared by a hand-written grep recorded in its journal. This turns that
one-off audit into a gate. Proven by injecting the same defect:

```
$ sed -i "s/{slide}/{Slide}/" src/runtime/locale/kz.ts
× has the same placeholders as en in every message 8ms
FAIL  |vue| test/utils/locale.spec.ts > locales > kz > has the same placeholders as en in every message
AssertionError: carousel.goto: expected 'Slide' to be 'slide'
Tests  1 failed | 101 passed (102)
```

### Placed at `test/utils/`, not `test/`
Upstream added `test/locale.spec.ts` and a `vitest.config.ts` include for the
`vue` project only. That is not available here: `test/vitest-include.ts` is
guarded by `test/utils/vitest-include.spec.ts`, which asserts **both**
directions — *"There is no declared vue-only category, so any such spec is a
mistake by definition"* — so a vue-only include would fail that guard, and a
top-level pattern would have to be added to both projects.

`test/utils/` already holds the repo-level structural specs (`theme.spec.ts`,
`skill-manifest.spec.ts`, `vitest-include.spec.ts`), and `utils/**/*.spec.ts`
is already in both projects' patterns. Putting the file there needs **no**
config change and satisfies the include guard by construction. 102 tests per
project, 204 total.

## Skipped
- **`cli/commands/make/locale.mjs`** — upstream now rejects any code CLDR does
  not know (*"the code for Tajik is tg, not tj"*) and defaults `--name` /
  `--dir` from CLDR. Ported here it would make `bitrix24-ui make locale`
  refuse `kz`, `tc`, `ua` and `vn` outright and silently mis-name `br`, `la`,
  `sc` and `in`. `--name` stays required.
- **`docs/.../SupportedLanguages.vue`** and **`docs/.../4.contribution.md`** —
  both upstream hunks rewrite the documented `make locale` invocation to drop
  `--name`, which follows from the CLI change we are not taking. Moot anyway:
  b24ui's docs do not document `make locale` at all (grep finds no occurrence
  in `docs/`), so there is no paragraph to edit. Adding one would be inventing
  fork documentation from upstream prose, not porting.

## Found while porting — not fixed here
`bitrix24-ui make locale` calls `sortFile(index.ts)` (`cli/utils.mjs`), which
does `file.trim().split('\n').sort()` over **every** line. Run against today's
`src/runtime/locale/index.ts` that is destructive: the file's `/** … */`
header and its blank lines sort to the top and the module is shredded.
Simulated — the sorted output does not equal the input, and the first lines
come back blank.

It is a real latent defect, but out of this commit's scope and not a
one-liner: inserting into a grouped file needs a rule for *which* group a new
locale joins, which is a maintainer call. Recorded here so it is not
rediscovered. The new spec does raise the alarm loudly if it ever fires — a
shredded index fails to parse and takes every locale test with it.
