# port — nuxt/ui@0317d508f077360724ccd4bb54d62b414088c334

**Upstream:** fix(FieldGroup): add `defaultVariants` in theme (#6938)

**Decision:** port — `src/theme/field-group.ts` matches upstream's pre-image in
the block the commit touches (same `size` keys plus the fork's extra `xss`, same
`orientation` keys), so the three lines apply verbatim.

## What it actually changes

Not the rendered DOM. All six `size` values in this theme are empty strings, so
`tv()` resolving `size` to `'md'` adds nothing — `FieldGroup.spec.ts` is
snapshot-identical before and after (22 tests, run both ways).

The effect is one level up, in `src/utils/theme.ts`:

```ts
if (defaultVariants.size && result.defaultVariants?.size && result.defaultVariants.size === 'md') {
  result.defaultVariants.size = defaultVariants.size
}
```

`applyDefaultVariants` rewrites a theme's size default from the module option
`b24ui.theme.defaultVariants.size` in `nuxt.config`, **but only for a theme that
already declares one**. `field-group.ts` declared none, so it was skipped
outright: a project that set `theme: { defaultVariants: { size: 'lg' } }` got it
applied to every other sized theme and silently not to `FieldGroup`. The block
makes the theme eligible.

`useComponentProps` is deliberately *not* part of this path — its proxy reads
`app.config.b24ui.fieldGroup.defaultVariants`, never `theme.defaultVariants`
(the comment at `useComponentProps.ts:73` says so). So the fix does not give
`props.size` a value, and the group still provides `size: undefined` to its
children when the prop is unset. That was true before the commit and stays true
after it; the commit's scope is the module option, nothing more.

## Test

Upstream ships none. Added a `applyDefaultVariants` block to
`test/utils/theme.spec.ts`, which already covered its sibling `applyUnstyled`:

- the real `field-group` theme, handed `{ size: 'lg' }`, comes back with
  `defaultVariants.size === 'lg'`
- a theme with a `size` variant and no `defaultVariants` comes back untouched —
  this is the guard that made the bug, asserted directly
- a theme pinning a non-canonical default (`xl`, `air-secondary`) keeps it

`applyDefaultVariants` mutates in place and themes are shared module exports, so
each case clones first.

## Coverage

| mutation | red |
| --- | --- |
| drop the `defaultVariants` block from `field-group.ts` | `rewrites a size default the module option was meant to reach`, in both the `vue` and `nuxt` projects |

Verified by reverting the three lines and re-running: 2 failed, 18 passed. The
other two cases are guards on `applyDefaultVariants` itself and stay green under
that mutation, as they should — they describe the function, not the theme.

## One thing checked and left alone

Scanning `src/theme/**` for a `size` variant without a `defaultVariants` block
turns up `dashboard-panel.ts`, but its `size` is a boolean variant
(`true` / `false`, controlling `w-full` vs `flex-1`), not a size token —
`applyDefaultVariants` would never have matched `'md'` there. After this port no
token-sized theme in the fork is missing the block.
