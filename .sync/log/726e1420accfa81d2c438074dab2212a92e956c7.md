# port — nuxt/ui@726e1420accfa81d2c438074dab2212a92e956c7

**Upstream:** fix(NavigationMenu): avoid duplicate accordion trigger on items without `to` (#6862)

**Decision:** port, verbatim in substance. Second of two commits taken together
(§6 4b), with `e4cb042b`.

## The defect

A vertical `NavigationMenu` item with `children` and no `to` renders its **whole
link** as the `AccordionTrigger` — there is no navigation to preserve, so the
button is the row. The trailing span was then made an `AccordionTrigger` as well,
nested inside the first.

Two triggers, one accordion item, so both receive the *same* generated id. The
snapshots show it plainly: `id="reka-accordion-trigger-v-1"` appears on the
`<button data-slot="link">` and again on the `<span data-slot="linkTrailing">`
inside it. That is invalid HTML, and it is not cosmetic — the content region's
`aria-labelledby` points at that id, so a screen reader following the reference
lands on whichever the browser resolves first.

## Upstream fix

A `trailingTrigger` flag threaded through the reusable link template. The
trailing element becomes an `AccordionTrigger` only when the flag is set, and
the call sites decide:

- the `label` branch passes `true` — a label is not a link, so nothing else can
  be the trigger;
- the three `B24LinkBase` branches pass `!!slotProps.href` — the link is a real
  anchor exactly when it has `to`, and only then does the trailing span need to
  be the trigger, because the anchor itself has to navigate.

`onLinkTrailingClick` takes the same flag: it swallows the click only when the
trailing span is the trigger. Without that, an item whose link is the trigger
had its own click cancelled by its own child.

## Snapshots

`renders with content orientation vertical correctly`, a fork case upstream has
no equivalent of. The delta is the same in all four and is exactly what the fix

`id`. Read before accepting rather than regenerated on faith.

## Tests

Upstream's two, adapted only in comments. Mutation-checked, and the four results
differ in a way worth recording — they show the flag has to both *exist* and
*vary*:

- reverting the `:is` gate (the defect itself) → **6 red**: both new tests and
  all four snapshots;
- passing `trailingTrigger` but hardcoding it `true` → **6 red**, the same set —
  a gate that never distinguishes is the defect;
- hardcoding it `false` → **2 red**: the `with to` case can no longer open, which
  is why this is a gate rather than a removal;
- dropping `&& trailingTrigger` from `onLinkTrailingClick` → **2 red**.
