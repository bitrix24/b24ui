# port — nuxt/ui@74ad017f045ac499683a4713efd0bb59ead543d7

**Upstream:** fix(Table): emit `aria-sort` on sortable th elements (#6879)

**Decision:** port — but not a plain one. This fork already had `aria-sort`,
added independently in `af408f59` (#554) ahead of upstream, with a predicate
that was wrong in four ways. Upstream's implementation replaces ours.

## What upstream does

Replaces a `getCanSort()`-only check with:

- `isSortable(column)` = `column.columnDef.enableSorting === true && column.getCanSort()`
- an early return on `header.isPlaceholder`
- a **single-column** rule: with several sort keys the direction goes to the
  first key that has a visible sortable header, and every other header reports
  `none`
- the helper takes the `Header`, not the `Column`

## Why this fork needed it — measured, not argued

Upstream's five new tests were added here **before** touching the
implementation. Four of them failed, and the failures name the defects exactly:

| failure | what it means |
| --- | --- |
| `expected 'none' to be undefined` | an ordinary accessor column with no sort UI announced itself as sortable-but-unsorted |
| `expected 'descending' to be 'none'` | with two sort keys, a direction was announced on **both** columns |
| (same test, hidden/unknown key) | the primary key was not chosen at all |
| `expected 'ascending' to be undefined` | placeholder cells in grouped headers carried the attribute |

The fifth passed: `getCanSort()` does correctly return false for
`sortingOptions: { enableSorting: false }` and for a display column.

**The #554 docblock asserted the opposite, in those words.** It said
`getCanSort()` "is the predicate, measured rather than assumed", and that
`aria-sort` is "absent everywhere else". It is absent for `enableSorting: false`
and for display columns — but it is **present** on every plain accessor column,
which is most of them. The measurement covered two cases and the conclusion was
written as if it covered all of them. The docblock now says which predicate is
needed and why, and records that it was wrong.

Scale of the defect, from the snapshot diff: **336** `aria-sort="none"`
attributes removed, plus 4 directional ones. 0 lines changed for any other
reason.

## Fork-only work upstream did not need

**The `aria-sort` describe block from #554 ran against the shared fixture**,
where no column sets `enableSorting: true`. That was fine while `getCanSort()`
alone decided; under the corrected predicate that fixture has no sortable column
at all, so the block would have asserted nothing while staying green. It now
opts the accessor columns in explicitly, which keeps what the block is actually
about — `select` opting out and `actions` having no accessor stay silent.

**Two console-gate adaptations.** Upstream has no gate; this fork fails any spec
that logs while rendering.
- `skips sort keys with no th on screen` deliberately passes
  `sorting: [{ id: 'unknown' }]`, and TanStack rightly logs
  `[Table] Column with id 'unknown' does not exist.` The noise is owned with a
  `vi.spyOn(console, 'error')` and asserted on, rather than exempting the file —
  which is what the gate itself calls a last resort.

**The docs `::note` from #554 carried the same wrong claim** and is corrected,
alongside upstream's new sentence about setting `enableSorting: true`.

## Docs and playground

The same four example columns as upstream gain `enableSorting: true` — found by
searching for `toggleSorting`/`getIsSorted` rather than by copying upstream's
line numbers. Without it those examples would offer a sort button and no
`aria-sort`, which is the defect this commit is about.

`highlights:` in `table.md` shift with the inserted lines: `[90, 115]` →
`[91, 116]` and `[109, 154]` → `[114, 159]`, each verified by checking that the
content previously on those lines is now on the new ones.

## A finding, not fixed here

Auditing those highlights showed **four** of the sixteen `highlights:` entries in
`table.md` point past the end of their example file — `table-columns-example`
(108 of 100), `table-row-context-menu-event-example` (173 of 172),
`table-column-sorting-reusable-example` (154 of 140) and
`table-column-pinning-example` (126 of 124). All predate this commit and none is
caused by it. Left alone: it is a docs-wide issue that would balloon a port PR,
and the one inside this commit's blast radius was shifted rather than silently
repaired, so it stays equally visible.
