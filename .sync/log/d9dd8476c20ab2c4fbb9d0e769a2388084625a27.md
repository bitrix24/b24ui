# port — nuxt/ui@d9dd8476c20ab2c4fbb9d0e769a2388084625a27

**Upstream:** chore(deps): move to pnpm catalog (#6956)

**Decision:** port — adopted, and it had to be, because the commit breaks this
fork's dependency-parity guard whether or not the catalog is adopted.

## Upstream change

`catalogMode: strict` and a `catalog:` block in `pnpm-workspace.yaml`; every
`dependencies` / `devDependencies` range in every manifest becomes `catalog:`.
`peerDependencies` stay literal — 30 entries, zero catalogued — because they are
the contract with consumers rather than what the repo installs.
`scripts/release.sh` also moves `npm publish` → `pnpm publish`, since only pnpm
resolves `catalog:` at pack time.

## The part that was not optional

`.sync/dep-parity.mjs` snapshots **upstream's** value for every package both
trees declare in the same section. After this commit those values are the literal
string `catalog:`. Measured before changing anything, by running the existing
generator at this cursor:

> **152 entries in the snapshot, 140 of them recorded as `"catalog:"`.**

That is the guard that exists because `prettier` sat at `^3.8.4` against
upstream's `^3.9.6` through four ported batches. Left alone it would have
compared a placeholder against our real ranges — 140 false drift reports — or,
had we adopted the catalog without fixing it, a placeholder against a
placeholder: green, and checking nothing.

So the tooling fix came first, and it applies on both sides:

- `.sync/dep-parity.mjs` resolves `catalog:` / `catalog:<name>` against
  upstream's `pnpm-workspace.yaml` at the cursor, and **throws** on a specifier
  the catalog cannot resolve rather than writing the placeholder through.
- `test/utils/dep-parity.spec.ts` resolves our own side the same way before
  comparing, and gained an assertion that no snapshot value may be a `catalog:`
  placeholder.
- `test/utils/peer-dependencies.spec.ts` needed it too: it reads
  `dependencies`/`devDependencies` to check the `reka-ui`/`vaul-vue` exact pins
  and that the dev Vue satisfies the peer range. Its docblock already anticipated
  this — *"a `workspace:*` or `catalog:` value carries no version"* — so it failed
  loudly instead of throwing, which is why it was found rather than passed.

## What adoption changed here

133 catalog entries across all 8 manifests. Of 133 distinct dependency names,
**130 already had a single range everywhere.** The three that did not:

| package | before | resolution |
| --- | --- | --- |
| `maska` | `^3.2.1` in docs+demo, `^3.2.0` in nuxt+vue | converged to `^3.2.1` |
| `tailwindcss` | `^4.3.3` everywhere, `^4.3.2` in demo | converged to `^4.3.3` |
| `@internationalized/date` | `^3.12.4`, `^3.9.0` in `playgrounds/vue` | named catalog `vue-legacy` |

The first two are live violations of §2 — *"a dep present in both [nuxt and demo]
must not drift"* — that the hand-kept invariant had missed. Adopting the catalog
is what surfaced them; a reviewer had not.

The third is a recorded deliberate hold: `playgrounds/vue`'s
`@internationalized/date` was "pinned older (`^3.9.0`) and diverges from
upstream's range, so left as-is" when `c19f1039` was ported. It goes in a **named**
catalog rather than staying literal, so the divergence is declared in the same
file as everything else instead of hiding in one manifest — which is the point of
moving versions here at all.

## Evidence

**Nothing new was installed.** Comparing every resolved `name@version` in the
lockfile before and after (peer-suffixes stripped, since those churn whenever any
peer in the chain moves):

- **added: 0**
- removed: 43

**42 of the 43 are deduplications** — a second copy dropped while another
survives: `@babel/*` 8.x alongside 7.29.x, `@shikijs/*` 4.2.0 alongside 4.4.3,
`@internationalized/date@3.12.2`, `maska@3.2.0`, `vue-router@5.1.0` and `5.2.0`,
`zod@4.4.3`, `valibot@1.4.1`, `joi@18.2.1`, and more.

The 43rd, `@types/jsesc@2.5.1`, lost every copy: it was a dependency of the
`@babel/generator@8.x` snapshots that went away, and nothing in the tree or any
manifest references it now.

**Worth a separate look later, not touched here:** `@nuxt/content@3.14.0` is gone
and only 3.16.0 remains. The `@nuxt/content>@nuxtjs/mdc` override in
`pnpm-workspace.yaml` justifies itself by that 3.14.0 copy existing, and its own
comment predicted that "a full lockfile regeneration might lift that peer and let
the override go". That is now worth re-measuring — deliberately as its own change,
not folded into a port.

## The publish path, and why it is now load-bearing

Upstream's `scripts/release.sh` moves `npm publish` → `pnpm publish` in this same
commit. There is no `scripts/release.sh` here — publishing runs from
`.github/workflows/npm-publish.yml`, and it already used
`pnpm publish --no-git-checks --provenance`. So that half needed no change.

It did need writing down. Verified both directions against the tarball rather
than the manifest:

- `pnpm pack` → the packed `package/package.json` carries **real ranges**:
  64 dependencies, 26 devDependencies, 13 peerDependencies, **zero** `catalog:`.
- the on-disk manifest, which is what a packer that does not understand catalogs
  would upload verbatim, carries **90** `catalog:` values.

So the difference between the two commands is now the difference between a
working package and one whose every install fails on metadata — and no gate in
this repository can see it, because the gate never publishes. A comment saying
exactly that now sits at the publish step, where somebody would edit it.
