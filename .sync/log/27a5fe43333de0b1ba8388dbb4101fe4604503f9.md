# port — nuxt/ui@27a5fe43333de0b1ba8388dbb4101fe4604503f9

**Upstream:** fix(vue): resolve explicit component imports to their Vue overrides (#6999)

**Decision:** port — `src/plugins/components.ts` matches upstream's pre-image
line for line in every hunk the commit touches. The fork-only block further down
(`packagesToScan` / `excludeRegex`) is untouched by it.

## The defect

The Vue adapter swaps certain components for Vue-compatible versions —
`Link` per router mode, and the color-mode pair — through a `resolveId` hook.
That hook only fired for **relative** imports made **from inside the runtime**:

```ts
if (!importer || !normalize(importer).includes(runtimeDir)) return
if (!RELATIVE_IMPORT_RE.test(id)) return
```

So `import Link from '@bitrix24/b24ui-nuxt/components/Link.vue'` in an app —
which the `"./components/*": "./dist/runtime/components/*"` export makes a
supported thing to write — resolved to the plain runtime component and quietly
skipped the override. Same for an absolute path, which is what an alias hands
over once Vite has substituted it.

## The fix

A branch ahead of the existing one, matching the specifier form
(`PACKAGE_IMPORT_RE`) or an absolute path under `runtimeDir/components/`,
extracting the path **relative to the components dir**, and looking it up with a
new `ComponentSource.resolvePath`. It returns early either way, so a path that
names no override falls through to normal resolution rather than being
reinterpreted by the relative-import branch below.

`resolvePath` matches the full relative path, not the basename that
`resolveFile` uses — that is what keeps `components/prose/Link.vue` from
resolving to the `Link` override.

## b24ui adaptation

`PACKAGE_IMPORT_RE` carries the package name, so it becomes
`@bitrix24\/b24ui-nuxt`. Verified against `package.json` rather than assumed:
this fork publishes the same two entry shapes upstream does —
`"./runtime/*": "./dist/runtime/*"` and
`"./components/*": "./dist/runtime/components/*"` — so `dist/`, `runtime/` and
the bare form all need to match here for the same reasons.

**This fork has no `Icon` component**, and upstream's new test drives every case
through `Icon.vue`. The override trees are otherwise identical:

```
upstream                                  b24ui
vue/components/Icon.vue                   —
vue/components/color-mode/ColorMode*.vue  vue/components/color-mode/ColorMode*.vue
vue/overrides/{inertia,none,vue-router}/  vue/overrides/{inertia,none,vue-router}/
```

So `Link.vue` stands in. That is not a cosmetic swap: `Icon` lives in
`vue/components`, `Link` in `vue/overrides/<router mode>`, so the router-mode
branch of `overrideSources` ends up carrying the cases upstream puts on the
plain one. The color-mode components cover the `vue/components` side, keeping
both branches exercised.

Two cases upstream has no occasion for:

- `LinkBase` is overridden for **inertia only**, so one specifier has to resolve
  differently per router mode — `vue/overrides/inertia/LinkBase.vue` under
  `router: 'inertia'`, and nothing under the default. Upstream's override dirs
  hold the same names in every mode.
- `colorMode: false` must keep the color-mode override unfound, so the app gets
  the plain component.

## Both adapters

Checked, per the repo rule that build-side changes are checked against
`src/module.ts` as well as `src/unplugin.ts` / `src/plugins/*`. `vue/overrides`
is referenced from `src/plugins/components.ts` and **nowhere else** in `src/`,
in this fork and in upstream alike (`git grep 'vue/overrides' origin/v4 -- src/`
returns only that file). The Nuxt adapter has no equivalent override mechanism —
Nuxt resolves `NuxtLink` natively — so there is no matching gap on that side.

## Coverage

`test/utils/components-plugin.spec.ts` is new, ported with the adaptations
above. Every case is mutation-checked:

| mutation | red |
| --- | --- |
| revert the whole `resolveId` branch | the three resolving cases (package, absolute, per-router-mode) |
| `resolvePath` → basename lookup (`resolveFile`) | `leaves other package imports alone` |
| `PACKAGE_IMPORT_RE` without the package prefix | `leaves other package imports alone` |
| drop `colorModeIgnore` from `unpluginComponents` | `does not override color-mode components when colorMode is off` |

The pre-existing relative-import case stays green under all four, as it should —
it covers the branch this commit did not touch.

**The negative cases were rewritten to be worth having.** Ported verbatim they
were vacuous here: upstream asserts `@nuxt/ui/components/Button.vue` and
`components/prose/Icon.vue` resolve to nothing, and in this fork *every*
plausible wrong implementation also returns nothing for them, because the
override set is four files and nothing collides. Confirmed by running the
basename mutation against the verbatim version — fully green. The committed
cases use `components/prose/Link.vue` (shares a basename with a real override)
and `some-other-lib/components/Link.vue` (has the exact tail the regex looks
for), each of which a looser implementation resolves. Both mutations above are
caught only because of that change.
