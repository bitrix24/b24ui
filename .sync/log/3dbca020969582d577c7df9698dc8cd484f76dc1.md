# Port: docs(mcp): add `x-mcp-tools` header to specify available tools

**Upstream:** `3dbca020969582d577c7df9698dc8cd484f76dc1` (nuxt/ui, #6788)
**Decision:** port — the server half; docs hunks have no counterpart here

## Upstream change
Two things under one title.

**1. A new `docs/server/mcp/index.ts`.** An MCP handler that reads an
`x-mcp-tools` request header and narrows the advertised tool list to the
comma-separated names in it, 400-ing on an unknown name. Clients with small
tool budgets can ask for a subset instead of taking all of them.

**2. Tool names in error messages corrected from snake to kebab.**
`list_examples` → `list-examples`, `list_templates` → `list-templates`, and the
`search_icons` reference in the docs. The toolkit derives the name clients see
from the filename, so the snake-cased strings named tools that do not exist —
an assistant told to "use the `list_examples` tool" would call nothing.

## b24ui port

### The handler
Ported verbatim into `docs/server/mcp/index.ts`, which the fork did not have —
until now every tool was advertised unconditionally. Checked the two things
that could have made it a no-op or a regression here:

- **`@nuxtjs/mcp-toolkit@0.18.1`** (bumped in `229b64f`) exports all three of
  `defineMcpHandler`, `getMcpTools` and `listMcpTools` from
  `@nuxtjs/mcp-toolkit/server`.
- **`orphansOnly: true`** only returns tools not attached to an MCP app.
  b24ui defines no apps (`grep defineMcpApp` → nothing), so every tool is an
  orphan and the filter changes nothing about what is advertised by default.
  Without that check the handler would have silently emptied the tool list.

`getHeader` and `createError` are nitro auto-imports; no imports needed.

### The stale tool names — same defect, both of ours wrong
Upstream's rename applies here too, against the fork's own tool names. Both
strings were wrong, and one was a half-converted hybrid:

```diff
- Use the b24_ui_list_templates tool to see all available templates.
+ Use the b24-ui-list-templates tool to see all available templates.
- Use the b24_ui_list-examples tool to see all available examples.
+ Use the b24-ui-list-examples tool to see all available examples.
```

Confirmed the real names rather than inferring them from the filenames:
grepping the generated docs server bundle
(`docs/node_modules/.cache/nuxt/.nuxt/dist/server/server.mjs`) returns
`"b24-ui-list-templates"` and `"b24-ui-list-examples"`. `docs/app/components/chat/Chat.vue`
already keys off the kebab form (`'b24-ui-search-icons'`), so the error strings
were the only place still spelling them with underscores.

## Where this actually takes effect
Worth stating plainly, because it is not what the upstream commit implies.
`deploy.yml` publishes the docs with `docs:full:generate` to **GitHub Pages** —
a static build. Server routes that cannot be prerendered are not part of that
output, and the generated tree confirms it: `docs/.output/public` contains no
`/mcp` endpoint and `.well-known/` holds only `skills`. So the MCP server —
this handler included — runs under `nuxt dev` and `docs:build`, not on the
published site.

Ported anyway: the handler is correct, it costs nothing, and it keeps the fork
from re-deriving the same code the next time someone runs the docs MCP server
locally or deploys them somewhere with a runtime.

Noticed while establishing that, and **not** acted on: `docs/nuxt.config.ts`
advertises `</.well-known/mcp/server-card.json>; rel="service-desc"` in a route
rule and exposes `mcpServer: ${baseUrl}/mcp/` in `runtimeConfig.public`, both
pointing at endpoints the Pages deploy does not serve. That predates this
commit and may well be deliberate — recorded as an observation, not a claim.

## Tests
No spec coverage for `docs/server/`. Two gates carry the weight:

- **`typecheck`** covers `docs` via `nuxt typecheck docs`, so the handler
  signature, the `getMcpTools` / `listMcpTools` option shapes and the index
  alignment between them are checked rather than merely linted.
- **`docs:generate`**, run out-of-band, is what proves the new server file does
  not break the build the site is actually published from — a malformed server
  route fails nitro's build step even though the route itself is dropped from
  the static output. `Prerendered 1240 routes`, exit 0 — unchanged.
