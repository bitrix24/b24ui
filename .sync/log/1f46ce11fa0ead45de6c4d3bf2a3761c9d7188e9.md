# Port: fix(components): prevent empty trailing slot when loading (#7027)

**Upstream:** `1f46ce11fa0ead45de6c4d3bf2a3761c9d7188e9` (nuxt/ui)
**Decision:** port

## Upstream change
In `useComponentIcons`, `trailingIconName` only gets the loading icon when `!isLeading`,
but `isTrailing` turned true for any `loading && trailing`. With a leading visual
present (upstream: `leadingIcon`), the loading icon went to the leading side and an
empty `trailing` span was still rendered. Upstream adds the same `!isLeading` guard to
`isTrailing`, plus an Input test case `with loading trailing and leadingIcon`.

## b24ui port
- `src/runtime/composables/useComponentIcons.ts`: the guard and its comment are applied
  verbatim to `isTrailing`.
- The fork's `isLeading` differs from upstream: it has no `leadingIcon` term (the fork's
  composable takes no `leadingIcon`) and it includes `avatar`. So in the fork the bug is
  reached through `avatar`, not `leadingIcon`: `loading + trailing + avatar` made
  `isLeading` true, the loading icon rendered leading, and the trailing span was empty
  (when no `trailingIcon`). The guard fixes that path.
- `test/components/Input.spec.ts`: upstream's `leadingIcon` case has no fork equivalent
  in the composable, so the fork adds `with loading trailing and avatar` instead (the
  fork had no `loading trailing` cases at all).
- Upstream's later 2fc9ba0 (spin trailing loading icon with avatar) is not part of this
  port.

## Tests
Snapshots not regenerated here: `Input.spec.ts.snap` and `Input-vue.spec.ts.snap` gain
the new entry. No existing spec renders `loading + trailing` together, so no other
snapshot should change.
