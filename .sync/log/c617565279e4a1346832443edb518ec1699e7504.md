# port — nuxt/ui@c617565279e4a1346832443edb518ec1699e7504

**Upstream:** fix(components): allow partial `ui` overrides on items (#6979)

**Decision:** port — taken for **parity**, not for effect. The change is
semantically inert on both sides, and that was measured rather than assumed.

## Upstream change

25 components get their per-item override widened:

```ts
- ui?: Pick<Accordion['slots'], 'item' | 'header' | …>
+ ui?: Partial<Pick<Accordion['slots'], 'item' | 'header' | …>>
```

filed as a fix for partial overrides being rejected by TypeScript.

## It changes nothing — here or upstream

`ComponentSlots` in `runtime/types/tv.ts` is

```ts
type ComponentSlots<T> = Id<{ [K in keyof T['slots']]?: SlotClass }>
```

Every slot key is **already optional**, and `Pick<>` preserves optionality. So
`Pick<Slots, 'a' | 'b'>` and `Partial<Pick<Slots, 'a' | 'b'>>` are the same
type. Those three lines are byte-identical in both repositories, so the defect
the commit describes does not exist on either side.

Measured, because "these look equivalent" is the reading that should not be
trusted:

- both directions of assignment between the two forms compile under `vue-tsc`
- a **control** using a genuinely required map fails the same assignment, so the
  probe can tell the difference when there is one

## Two tests written and then removed

Both looked like evidence and checked nothing. Reverting `Partial<` in a
component left both green — which is consistent with there being nothing to
assert, but only after the probe above explained *why*.

1. `expectTypeOf<{ trigger: string }>().toExtend<…>()` — doubly inert: it raises
   nothing under plain `vue-tsc`, and at runtime it is a no-op unless vitest
   runs in typecheck mode, which this suite does not.
2. An annotated `const item: AccordionItem = { b24ui: { trigger: 'p-0' } }` —
   checked by `vue-tsc` (a deliberate `const x: number = 'y'` in the same file
   does fail it), but it passes either way, because the two types are equal.

Recorded rather than quietly dropped: a green type test over an already-true
proposition is the exact shape of a test that reads as proof of a fix.

## What is kept, and why

`test/utils/item-ui-partial.spec.ts` holds every component to upstream's
spelling. It is labelled a **parity rule** in its own docblock and states that no
behaviour depends on it, so it cannot later be mistaken for a guard against a
real defect.

The reason to keep the change at all is the reason the sync exists: a file that
diverges from upstream in spelling is a file where the next patch does not apply
cleanly. The rule extends that to the next component somebody adds.

## Scope here is 22 files, not 25

Arithmetic, checked rather than assumed: upstream's 25, minus four components
this fork does not have — `Carousel`, `Tree`, `PageAnchors`,
`content/ContentNavigation`, all on the upstream-only list in AGENTS.md — plus
one it has and upstream does not, `DescriptionList`, which carried the same
spelling. 25 − 4 + 1 = 22.

Every changed line was verified to be exactly a `Partial<>` wrap and nothing
else: 22 removed, 22 added, 0 unexplained.
