# port — nuxt/ui@7f0250eab69d04c42e137aa85c103e3dc83eec60

**Upstream:** fix(EditorToolbar): use tooltip text as `aria-label` on icon-only buttons (#7009)

**Decision:** port, adapted — the fork's `getButtonProps` differs from
upstream's parent in the defaults it passes: this fork's toolbar has no
`variant` / `activeVariant`, only `color`, `activeColor` and `size`. The new
`'aria-label'` default was added to the fork's own object; the other keys were
kept as they are here, quoted as upstream quotes them (one quoted key makes
`quote-props` require all of them).

## The defect

The documented way to configure an icon-only toolbar button is an `icon` plus a
`tooltip`. A tooltip is a pointer-hover affordance: it never reaches assistive
technology. So those buttons had **no accessible name** — a screen reader
announced "button" and nothing else.

## The fix

```ts
'aria-label': baseProps.label ? undefined : item.tooltip?.text,
```

inside `defu(baseProps, { … })`, so:

- an item with a visible `label` is not relabelled on top of its text;
- an author-supplied `aria-label` on the item wins, because `baseProps` is
  `defu`'s first argument;
- dropdown triggers get the same treatment, since they go through
  `getButtonProps` too.

`TooltipProps` here has `text?: string` (`Tooltip.vue:14`), and `B24Button`
forwards `aria-label` to the rendered `<button>` through `$attrs` — the test
reads it off the element, not off props.

## b24ui adaptation of the test

Upstream's two cases were added to `test/components/EditorToolbar.spec.ts`
with this fork's icons — `BoldIcon`, `ItalicIcon`, `UnderlineIcon`,
`StrikethroughIcon`, `HeaderIcon` from `@bitrix24/b24icons-vue`, already
imported by the spec — in place of `i-lucide-*` strings, and
`B24EditorToolbar` in the `TooltipProvider` wrapper. The heading child drops its
icon string.

Added **before** the source change: 4 red (both cases, both projects) —
`expected undefined to be 'Bold'`, `expected undefined to be 'Headings'`.
