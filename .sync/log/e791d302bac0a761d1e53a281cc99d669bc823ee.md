# port — nuxt/ui@e791d302bac0a761d1e53a281cc99d669bc823ee

**Upstream:** fix(Select/SelectMenu): add responsive text size (#6903)

**Decision:** port, component half only — the theme half is n/a and taking it
would be a regression.

## Upstream change

`Input` and `InputMenu` had a `fixed` prop; `Select` and `SelectMenu` did not, so
their text size could not be held at the mobile value. Two halves:

- **Components.** `fixed?: boolean` added to both prop interfaces and passed into
  `tv()`; `SelectMenu` also forwards it into `searchInputProps` so the field
  inside the menu follows the same setting.
- **Theme.** `base` deleted from all five size variants in `select.ts`, so the
  base sizing falls through to the `input` theme it extends — which is where the
  responsive rule lives.

The point of the feature is iOS Safari: it zooms the page when a text control
under 16px takes focus, so the mobile size is the larger one and `md:` steps it
back down. `fixed` opts out of that step.

## b24ui port

**The component half applies exactly.** Both files carry upstream's pre-image —
`highlight?: boolean` with no `fixed` after it, and a `tv()` call with
`highlight: highlight.value` and no `fixed` — so the three hunks land as written.
`SelectMenu`'s `searchInputProps` differs in its defaults (`type: 'text',
size: 'md'` here against upstream's `variant: 'none'`), but that is the object
upstream adds `fixed` to, and the addition is the same.

One deliberate wording change. This fork's `fixed` on `Input.vue` and
`InputMenu.vue` is documented *"Keep the mobile text size on all breakpoints.
(Left for backward compatibility.)"*. The parenthetical was not copied: on
`Select` the prop is **new**, not inherited, and carrying that note across would
say something false about it.

**The theme half is not applicable, and taking it would break sizing.** Upstream
deletes `base` from each size so the value comes from the `input` theme. Ours
already inherits the *responsive* part — `theme/select.ts` extends `input` through
`defuFn`, and the compound variants pairing `fixed: false` with each size come
with it. Verified by reading rendered output rather than the theme source: the
committed `Select` snapshots already carry `md:text-(length:…)` in 44 places, and
`SelectMenu` in 96, before any of this.

What our `base` lines carry on top is not upstream's: `h-[28px] gap-1.5
text-(length:--ui-font-size-xs)/[normal]` — explicit heights and this fork's own
font scale, one step off `input`'s at several sizes, plus an `xss` size upstream
has no equivalent of. Deleting them would change the height of every Select in
the library. So the fork was missing exactly one thing, and it is the thing the
component half adds: the lever to turn the responsive step off.

## Tests

The prop's whole effect is a class that is **absent**, and no snapshot moves —
`fixed` defaults to unset, so the default render is unchanged. Snapshot cases
would therefore have pinned the classes without stating what the prop is for, and
would keep passing if the responsive rule stopped reaching `Select` altogether.
Three assertions per component instead:

- the responsive `md:text-(length:…)` override is present by default;
- it is gone with `fixed`;
- the un-prefixed size class survives **both** ways — a guard against the obvious
  wrong fix, which is to drop the base size rather than the override, and which
  would satisfy the second assertion while leaving the control with no size.

Mutation-checked rather than assumed. Removing `fixed: props.fixed` from both
`tv()` calls — the port itself — turns **2** red, the two that pin the new
behaviour. Inverting it to `!props.fixed` turns **101** red, snapshots included,
which confirms the wiring reaches rendered output rather than stopping at the
props object.

**Recorded rather than fixed here:** `fixed` on `Input` and `InputMenu` has no
test at all and has been shipping uncovered since it was introduced. Out of scope
for a port of a Select commit, but it is the same prop and the same mechanism, and
the assertions above transfer directly.
