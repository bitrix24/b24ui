# port — nuxt/ui@9ea37c1653cf0fdae78a2edd7dd95fcb85b2a033

**Upstream:** fix(SelectMenu/InputMenu): ignore clear button when disabled (#6986)

**Decision:** port — both components exist here with the same `clear` wiring, and
the defect is present verbatim.

## The defect

With `clear` set, a disabled `SelectMenu` or `InputMenu` still rendered its clear
button, and clicking it still emitted `clear`. A disabled field that can be
cleared is a disabled field that is not disabled.

## The fix

Two halves, in both components:

```ts
function onClear() {
  if (disabled.value) {
    return
  }

  emits('clear')
}
```

and `!disabled` added to the `v-if` on `Component.Cancel` / `ComboboxCancel`.

Our `onClear` is byte-identical to upstream's pre-image, and so is the `v-if`
modulo `ui` → `b24ui`, so both hunks transfer directly.

`disabled` is already in scope in both, at line 332:
`computed(() => formFieldDisabled.value ?? props.disabled)`. That is a quiet
improvement over a literal reading of upstream's patch — the fix covers a field
disabled by its surrounding form, not only one disabled by its own prop.

## Where upstream's tests could not be used as written

Upstream finds the button with `[data-slot="trailingClear"]`. **That marker never
reaches the DOM in this fork.** `Button.vue:222` puts a static
`data-slot="base"` on its root and that wins over the fallthrough attribute, so
`data-slot="trailingClear"` is swallowed while the `trailingClear` *class* still
merges — visible in `InputMenu.spec.ts.snap`, where the `with clear` case renders
the close icon on a `data-slot="base"` element carrying `p-0`.

Measured rather than inferred: `trailingClear` occurs **0 times** across the
snapshot file, in a fork where the attribute is written in the template. A probe
with three model-value shapes (the item object, its `value`, its `label`) found
the button under none of them.

So the ported tests address the button by position — the only `data-slot="base"`
inside `data-slot="trailing"` — because that is what the fork actually renders.

**Recorded, not fixed here.** Making `data-slot` pass through would change what
every `B24Button` consumer renders and belongs in its own change; AGENTS.md's
"add `data-slot` attributes on all elements" says the marker is meant to be
there, so this is a real divergence rather than a style choice.

## Coverage, including where it was NOT achieved

| mutation | result |
| --- | --- |
| drop `!disabled` from the `v-if`, both components | **8 tests red** — the prop test and the form test, in both components, in both projects |
| force the `v-if` false | red — the positive test is not vacuous (two existing snapshots also catch it) |
| **drop the `onClear` guard, both components** | **360 passed — nothing red** |

The last row is the finding. `onClear` has exactly one call site in each
component — `@click.stop` on the button inside the very `v-if` this commit gates
on `!disabled` — and it is not in `defineExpose`. Once the template half lands,
**the guard is unreachable through the component's own surface**, so no test can
cover it and none was written to pretend otherwise.

It is ported anyway, deliberately: it is upstream's line, dropping it would
diverge the file for no measured gain, and it is the kind of guard that starts
mattering the moment another call site appears.

## A fork-only test that upstream has no counterpart for

`does not render the clear button when the form is disabled` — because
`formFieldDisabled` feeds the same `disabled`, and upstream's two tests both stay
green with the `v-if` reading `!props.disabled` instead. It goes red under the
M1 mutation above, so it is load-bearing rather than decorative.

Worth recording how it was got right: the first version put `disabled` on
`B24FormField` and failed. `B24FormField` has **no** `disabled` prop — the flag
reaches `useFormField` from `B24Form` through `formOptions`
(`useFormField.ts:127`, `formOptions?.value.disabled || props?.disabled`). The
test now sets it on the form. A failing test caught an assumption that would
otherwise have been written into a passing one.
