# Port: feat(vue): support `experimental.componentDetection`

**Upstream:** `3a568b5e582dd24f233a09f72e002566bb8bd6b9` (nuxt/ui, #6731)
**Decision:** port — the whole feature, plus two defects it surfaced here

## Upstream change

`experimental.componentDetection` scans the app, finds which components are
actually used, and narrows the generated theme CSS to those plus their
dependency closure. It only ever worked under Nuxt. This commit makes it work in
the Vue (unplugin) integration, and fixes several things in the scanner along
the way.

**The mechanism differs between the two integrations, for a reason worth
keeping.** Nuxt narrows the `@source` list to the detected components' template
files. The Vue plugin cannot: its templates live inside `node_modules`, where
Tailwind widens a file `@source` to a scan of the whole parent directory, so a
narrowed list would not narrow the CSS. It sources the whole directory and
instead **blanks the theme of undetected components at write time** — the same
transformation `theme.unstyled` performs. The files still exist, because the
`#build/*` aliases and the type imports need them to.

Scanner fixes in the same commit:

- **kebab-case tags.** `<u-button>` is mandatory for in-DOM templates and was
  never matched. The kebab alternative only matches as a *tag*; bare kebab
  identifiers in scripts and prose would match far too much ordinary text.
- **Prose shadowing.** The dependency graph is keyed by file basename, and prose
  components share basenames with regular ones. Letting them into the graph
  overwrote the regular component's dependency set. Now `prose/**` is ignored.
- **Phantom graph edges and phantom detections.** The pattern matches ordinary
  identifiers, so edges and detections are filtered against real component files.
  `includeComponents` names are filtered too, and unknown ones now warn.
- **Declaration files.** `components.d.ts` declares every component ever
  rendered; scanning it kept anything used once detected forever.
- **`.mts` / `.mjs` / `.cjs`** added to the scan glob and the dev watcher.
- **`resolveExtraScanDirs`** — packages from `scanPackages` live in
  `node_modules` (which the root scan skips) and `components.dirs` can point
  outside the root; both are now scanned. Build-output ignores are skipped for
  package dirs, since published packages ship their code in `dist/`.

## b24ui port

Ported in full. The fork's divergences are all in the plumbing, not the logic:

- `getTemplates(options, nuxt?, resolve?)` gains the `vue` parameter as its
  fourth rather than fifth argument — this fork dropped upstream's unused
  `uiConfig` parameter in an earlier port.
- `TemplatePlugin(options)` gains `componentDir` as its second rather than third
  argument, for the same reason (`appConfig` is not threaded through it here).
- `Bitrix24UIOptions` stops omitting `experimental`, which is what made the
  option unreachable from the Vue plugin.
- `consola` rather than `@nuxt/kit`'s `logger` in `utils/components.ts` and the
  Vue plugin: both run outside Nuxt, and this file must not drag `@nuxt/kit`
  into a Vue build. `templates.ts` keeps `logger` — it is Nuxt-only there.
- The scan prefix is the literal `'B24'` at both call sites. This fork has no
  configurable component prefix (upstream's `prefix` option), so the graph pass
  and the app scan happen to agree today; the graph still fixes its own pattern
  to `B24`, as upstream fixes its own to `U`.
- `kebabCase('B24')` is `'b24'`, so the kebab alternative matches `<b24-button>`
  and `<lazy-b24-tooltip>` as intended. Verified rather than assumed.

Upstream's `PageCTA` acronym case has no counterpart: this fork has no component
whose name contains an acronym.

## Two defects this surfaced

**`playgrounds/vue/tsconfig.app.json` had a broken alias.** It read
`"#build/b24ui": ["./node_modules/.b24ui-nuxt/b24ui/*"]` — a wildcard on the
value with none on the key, plus a trailing comma. TypeScript treats a
pattern without `*` as an exact match, so `#build/b24ui/button` never resolved
through it. Upstream's commit adds the same alias, correctly; taken as the fix.

**The docs named a component that does not exist.** Both installation guides
show `componentDetection: ['Modal', 'Dropdown', 'Popover']`. There is no
`Dropdown` in either project — it is `DropdownMenu`. Upstream fixed its own copy
here; this fork's copy needed the same. That used to be harmless, and is not any
more: unknown names in `includeComponents` now warn.

## One deliberate divergence

Upstream keeps the scanned-extension list as a literal in two places — the scan
glob and the `builder:watch` filter — and had to edit both in this commit when
`.mts`/`.mjs`/`.cjs` were added. An extension in one and not the other means a
file that changes the answer never triggers a refresh: no error, no signal.

Exported as `COMPONENT_DETECTION_EXTENSIONS` from `utils/components.ts` and used
by both. This fork had already split `COMPONENT_DETECTION_WATCH_RE` out for the
same reason, so the pattern is not new here.

## Tests

`test/utils/components.spec.ts` (new) — upstream's spec, adapted. Real temporary
directories rather than a mocked `fs`, because half of what is checked *is* glob
and module-resolution behaviour, which a mock would define away.

Two tests are this fork's rather than upstream's:

- **`does not build graph edges to names that are not components`.** Upstream's
  spec does not cover the graph-edge filter — verified by deleting it and
  watching all 38 tests still pass. It needs a stand-in component directory:
  the real tree has no component that mentions a `B24`-prefixed non-component,
  so no fixture under `src/` can show the difference.
- **`componentDetection examples in the docs name components that exist`** —
  the `Dropdown` defect above, now guarded.

Upstream's `PageCTA` test is dropped (no acronym components here) and its
`URL`/`UUID` junk-identifier fixture is replaced with `B24Config`/`B24Endpoint`:
with a `B24` prefix, `URL` does not match. First attempt used `B24Theme` — which
turns out to be a real component in this fork, so the test failed and said so.

`test/utils/templates.spec.ts` — the extension test now iterates
`COMPONENT_DETECTION_EXTENSIONS` instead of a five-item literal, and a second
test asserts the glob still reads from the same constant, so the two cannot
drift back apart with every test green.

Mutations tried, **each red**: drop the `prose/**` ignore; drop the graph-edge
filter; drop the `validComponents` filter; stop ignoring `*.d.ts`; drop the
kebab alternative from the pattern; make the graph follow the scan prefix; apply
build-output ignores to package dirs; point the watcher at a literal; point the
glob at a literal; put `Dropdown` back in the docs.

## End-to-end check

Built `playgrounds/vue` with `componentDetection: true` — a real test of
`resolveExtraScanDirs`, since that playground's `components.dirs` points at
`../nuxt/app/components`, outside the Vite root:

```
[success] Bitrix24 UI detected 43 components in use (including dependencies)
```

`node_modules/.b24ui-nuxt/b24ui/color-picker.ts` comes out with every slot
blanked; `button.ts` does not.

The CSS saving on that playground is **modest and worth stating honestly**:
599,544 → 596,929 bytes, about 0.4%. It uses 43 components, and most of the
bundle is shared utilities and design tokens rather than per-component classes.
The feature does what it says; the headline number depends entirely on how much
of the library an app leaves unused.
