**Upstream:** test: raise timeouts for slow windows runners

**Decision:** no-op — both counterparts exist, and neither raise buys anything
here, because this fork's CI has no Windows runner to be slow on.

## What upstream changed

Two timeout raises, both aimed at `windows-latest`:

```ts
// test/components/Toast.spec.ts
await vi.waitFor(() => …, { timeout: 4000 })

// test/utils/components.spec.ts
// Scanning the fixtures is far slower on the Windows runners.
describe('detectUsedComponents', { timeout: 20000 }, () => {
```

## Why it is a no-op here

Upstream's `module.yml` runs its main job on
`os: ${{ github.event_name == 'pull_request' && fromJSON('["ubuntu-latest"]') || fromJSON('["ubuntu-latest", "windows-latest"]') }}`
— Windows on push. Every workflow in this fork pins `ubuntu-latest`:
`ci.yml`, `npm-publish.yml`, `pr-title.yml`, `release-please.yml`,
`release-watchdog.yml` and `smoke.yml` hard-code `runs-on: ubuntu-latest`, and
`deploy.yml` is the only one with a matrix — `os: [ ubuntu-latest ]`.

Measured on the runner OS this fork actually uses, rather than assumed:

| test | measured | default | headroom |
| --- | --- | --- | --- |
| `detectUsedComponents` slowest case | 206 ms | 5000 ms | 24× |
| `Toast > calls onClick once per click` | 68 ms | 1000 ms (`vi.waitFor`) | 14× |

Applying the raises would not change a single outcome; it would only make a
genuinely hung test take 4 s or 20 s to say so instead of 1 s or 5 s.

**Revisit this entry if a Windows runner is ever added to `ci.yml`** — at that
point the raises stop being decoration and the upstream reasoning applies
verbatim.
