# port — nuxt/ui@27a3ef7ea5f688b42815595e6c49469f900e3a20

**Upstream:** fix(InputMenu): ignore `multiple` in autocomplete mode (#6971)

**Decision:** port — the fork has the same `mode: 'autocomplete'` branch and the
same scattered `props.multiple` checks.

## The defect

`autocomplete` mode already omits `multiple` from the props forwarded to
`ComboboxRoot` (via `rootPropsOmitted`), so the combobox itself is single-select.
But the rest of the component kept reading `props.multiple` directly, so setting
both produced a half-state: the `multiple` theme variant applied, `Component.Anchor`
stopped rendering `as-child`, and the markup diverged from plain autocomplete
while the behaviour did not.

## The fix

One derived flag, used everywhere the component branches on multi-select:

```ts
const isAutocomplete = computed(() => props.mode === 'autocomplete')
// `multiple` doesn't apply in autocomplete mode.
const isMultiple = computed(() => !!props.multiple && !isAutocomplete.value)
```

Two sites change meaning — the theme variant `multiple: isMultiple.value` and
`<Component.Anchor :as-child="!isMultiple">`. Two more are pure refactors:
`ComboboxRoot :as-child` and `TagsInputRoot v-if` already spelled the same
condition out by hand.

Left alone deliberately: `props.multiple` in the model-value logic, which
upstream also keeps as-is — that code is reached through the combobox's own
single/multiple wiring, not through the markup branch.

## b24ui adaptation — a fork-only site upstream does not have

The fork renders a `tag` badge that upstream has no equivalent of, and it renders
it **twice**: once before `Component.Anchor` and once inside `TagsInputRoot`.
Those two guards were `!props.multiple` and `!!props.multiple` — a partition of
`props.multiple`, so exactly one fired.

Once `TagsInputRoot` is gated on `isMultiple`, that partition breaks: with
`multiple` **and** `autocomplete`, the outer badge is suppressed by
`!props.multiple` and the inner one is unreachable because its container no
longer renders. The tag disappears entirely.

Confirmed before fixing it — a probe with the outer guard left as
`!props.multiple` gave `expected [] to have a length of 1 but got +0`. Both
guards now follow `isMultiple`.

## Coverage

| mutation | caught by |
| --- | --- |
| `multiple: isMultiple.value` → `props.multiple` | `with autocomplete mode ignores multiple` |
| `:as-child="!isMultiple"` → `!props.multiple` | same test |
| outer badge `v-if="!isMultiple && isTag"` → `!props.multiple && isTag` | `with autocomplete mode still renders the tag when multiple is set` |

**One mutation is not caught, and it is equivalent rather than untested:**
changing the inner badge's `v-if="isMultiple && isTag"` to
`!!props.multiple && isTag` leaves all 176 tests green. It has to — that badge
lives inside `TagsInputRoot`, which itself renders only when `isMultiple` is
true, and `isMultiple` can only be true when `props.multiple` is truthy. Inside
that subtree both spellings reduce to `isTag`. Recorded here so the gap is not
mistaken for a missing test.

The two refactored sites (`ComboboxRoot :as-child`, `TagsInputRoot v-if`) are
likewise equivalent by construction — `isMultiple` is literally the expression
they used to spell inline — so no mutation of them can be caught either.
