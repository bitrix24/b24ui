## Upstream change

`packageManager` `pnpm@11.27.0` → `pnpm@12.4.2`, plus the lockfile pnpm 12
rewrites on the next install (+1000/-122 lines there).

## What pnpm 12 does to the lockfile

The format is not migrated — `lockfileVersion` stays `'9.0'` on both sides. What
changes is that the file becomes **two YAML documents**:

| | doc 0 | doc 1 |
| --- | --- | --- |
| keys | `lockfileVersion`, `importers`, `packages`, `snapshots` | `lockfileVersion`, `settings`, `overrides`, `importers`, `packages`, `snapshots` |
| holds | pnpm managing itself | the project's own graph |

Doc 0 is new: the root importer gains `configDependencies: {}` and
`packageManagerDependencies: pnpm: {specifier: 12.4.2, version: 12.4.2}`, and the
14 `@pnpm/exe.*` platform binaries are recorded as packages. Doc 1 is the previous
file, unchanged.

Our result is structurally identical to upstream's: `---` at lines 1 and 158 in
both, same top-level key order in both documents. It parses as valid
multi-document YAML.

## Evidence

**No dependency moved.** Extracting every `name@version` package key from the
lockfile before and after gives 2239 → 2254 entries:

- **added, 15**: `pnpm@12.4.2` and the 14 `@pnpm/exe.*` binaries
- **removed, 0**

Nothing else resolved differently, which is what a package-manager bump should
look like and is not something to take on faith across a major.

**The load-bearing pins all held** — checked individually rather than inferred
from the count above, because each has an incident behind it:

| --- | --- |
| `happy-dom` | 20.12.0 — the exact pin from the `dep-parity` bisection |
| `vite` | 8.2.1 |
| `rolldown` | 1.2.3 |
| `tailwind-variants` | 3.2.2 |

| `prosemirror-view` | 1.42.3 |
| `@nuxt/image` | 2.0.0 |
| `@nuxtjs/mdc` | 0.23.1, single copy |

`settings:` and `overrides:` survive in doc 1, so the whole
`pnpm-workspace.yaml` override block still applies.

**`pnpm install --frozen-lockfile` passes** under 12.4.2, and prints an explicit
`✓ Lockfile passes supply-chain policies (1801 entries in 4.2s)`.

**Nothing in the repo parses the lockfile**, so the new `---` preamble cannot
break a local tool; `.sync/dep-parity.mjs` reads the manifests, and
`.github/scripts/assert-lockfile-frozen.py` reads the workflows. Both pass.

**Every workflow follows automatically.** All five — `ci`, `deploy`,
`npm-publish`, `smoke`, `pr-title` — use `pnpm/action-setup` with no version
input, so they read `packageManager`. That line in `package.json` is the only
place the version is named.

## One real failure, caught by a guard

`test/utils/governance-files.spec.ts > CONTRIBUTING.md > quotes the pinned pnpm
version` went red on the bump: `CONTRIBUTING.md:58` still said **pnpm** `11.20.0`.
Updated to `12.4.2` and green.

That is the guard doing exactly what its docblock says it is for — "prose does not
run, and `documented-scripts.spec.ts` only checks script names, so a
`packageManager` bump would leave the doc wrong with nothing red anywhere". No
mutation was needed to establish it: it went red on a real bump and green on the
real fix.

The one other version-specific sentence in the docs was checked and left alone.
`docs/content/docs/1.getting-started/6.integrations/5.content.md:113` says pnpm 11
removed `onlyBuiltDependencies`/`ignoredBuiltDependencies` in favour of the
approve-builds map — a statement about *when* that happened, still true, and
`allowBuilds` in `pnpm-workspace.yaml` still works under 12.
