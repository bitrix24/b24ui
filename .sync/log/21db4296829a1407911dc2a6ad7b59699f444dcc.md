# Port: docs(ComponentCode): fix number input after clearing

**Upstream:** `21db4296829a1407911dc2a6ad7b59699f444dcc` (nuxt/ui, #6805)
**Decision:** port — adapted (same bug, different control structure here)

## Upstream change
The playground's prop editor decided an input's `type` from the **current**
value on every render:

```diff
-              :type="option.type?.includes('number') && typeof getComponentProp(option.name) === 'number' ? 'number' : 'text'"
+              :type="option.inputType"
```

with `inputType` now computed once, from the *original* prop value:

```diff
+    const type = props?.cast?.[key] ?? prop?.type
+
       name: key,
       label: key,
-      type: props?.cast?.[key] ?? prop?.type,
+      // Determined from the original value so clearing a number input doesn't turn it into a text one
+      inputType: type?.includes('number') && typeof get(props.props, key) === 'number' ? 'number' : 'text',
```

Clearing a number field makes the value `undefined`, so `typeof … === 'number'`
turned false and the input became a text one mid-edit — the stepper vanished
and it never came back.

## b24ui port — the same bug, but worse here
b24ui's `ComponentCode.vue` has diverged: it does not flip one input's `type`,
it picks **between two different components** on the same condition —
`B24InputNumber` when the value is a number, falling through to `B24Input`
otherwise:

```diff
-              v-else-if="option.label === 'content.sideOffset' || (option.type?.includes('number') && typeof getComponentProp(option.name) === 'number')"
+              v-else-if="option.label === 'content.sideOffset' || option.inputType === 'number'"
```

So clearing the field did not merely change an attribute — the `v-else-if` went
false and Vue **swapped the component**, unmounting `B24InputNumber` and
mounting `B24Input` in its place. That loses focus as well as the stepper, so
the fix matters more here than upstream, not less.

The `options` computed gains the same `inputType`, derived the same way — from
`props.props`, the original MDC props, not from the live `componentProps`
state. `type` is kept alongside it because the `B24Switch` branch above still
reads `option.type?.includes('boolean')`.

Two things deliberately left as they are:

- **The `content.sideOffset` special case.** It is an unconditional `||` in
  front of the number test and unrelated to the value's type; folding it into
  `inputType` would change which control that one prop gets.
- **The boolean branch.** `option.type?.includes('boolean') && typeof
  getComponentProp(…) === 'boolean'` re-reads the live value too, but a
  `B24Switch` only ever emits `true`/`false`, so it cannot fall out of its own
  branch the way a cleared number field can.

## Tests
Docs-only; `docs/` has no spec coverage and nothing under `test/` touches this
component. The suite is unchanged by construction. The behavioural check is the
docs build plus the manual path: open any component page with a numeric prop
(`sideOffset`, `max`, `min`), clear the field, and the stepper stays.

## Verify (CI=true)
`lint` · `typecheck` · `test` · `build` — all green. `typecheck` is the one that
carries weight here: it covers `docs` via `nuxt typecheck docs`, so the new
`inputType` field and its template use are checked, not just linted.
