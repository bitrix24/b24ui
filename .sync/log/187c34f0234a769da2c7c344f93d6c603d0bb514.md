# port — nuxt/ui@187c34f0234a769da2c7c344f93d6c603d0bb514

**Upstream:** fix(Table): make rows with a select event keyboard accessible (#6838)

**Decision:** port — the fork matches upstream's pre-image in all four places.

## The defect

A row with `onSelect` already got `tabindex="0"`, so it could be focused — and
nothing happened when it was activated. There was no `keydown` handler at all;
only `@click` called `onSelect`.

This closes a gap left half-open by #614. That change gave selectable rows a
focus outline that actually paints, on the reasoning that `tabindex="0"` makes
them focusable. It does — so after #614 a keyboard user could **see** focus land
on a row that could not be operated. Both halves are now in place.

## The fix, in four parts

1. `@keydown.self.exact.enter.space` on the row, so Enter and Space select.
2. `:role="props.onSelect ? 'button' : undefined"` is **removed**. A `<tr>` with
   `role="button"` stops being a row for assistive technology, which is a worse
   trade than the one it was making.
3. `isInteractive` widens from `button, a` to
   `a, button, input, label, select, textarea`, so a click inside a nested
   control no longer selects the row.
4. An early return on `(e as KeyboardEvent).repeat`, so holding the key does not
   fire repeatedly.

`.self` and `.exact` do real work: `.self` keeps the handler from firing when the
event started in a nested control — which is also why no `[contenteditable]`
entry is needed in the selector — and `.exact` blocks modified presses, so
Cmd-Enter or Shift-Space stay available to the browser.

## Measured before fixing

Upstream's tests were added here **before** touching the implementation. Five of
six failed, which is the defect stated as a list.

## One upstream test deliberately not ported

`passes accessibility tests with select event` fails in this fork for a reason
that has nothing to do with this commit, so porting it would have meant shipping
a red test or a false attribution.

axe reports **`aria-hidden-focus`** — "ARIA hidden element must not be
focusable" — on `<thead>` and every `<tr>`, because this fork's test environment
renders the table inside an `aria-hidden="true"` subtree. Evidence that it is
pre-existing and environmental:

- `data-aria-hidden` occurs **168 times** in the committed Table snapshots
- `tabindex="0"` on selectable rows predates this commit, so the rule fires on
  the pre-image too
- it fails with the test run in **isolation**, so it is not another spec leaking
  an open overlay

Recorded rather than worked around. The rows keep their axe coverage through the
existing `passes accessibility tests`; what that one lacks is a focusable row
for the rule to catch. Worth a separate look at why the fork's test environment
marks the tree `aria-hidden` at all.

## Coverage

Each part is pinned by a different test:

| mutation | red test |
| --- | --- |
| remove the `keydown` handler | `calls select on Enter and Space` (+ others) |
| restore `role="button"` | `calls select on Enter and Space` — its `role` assertion |
| narrow `isInteractive` back | `does not call select from nested controls` |
| remove the `repeat` guard | `does not call select on repeated keydown` |
| drop `.exact` | `does not call select when a modifier key is held` |
| drop `.self` | `does not call select from a nested contenteditable` |

No snapshot moves: `role` only ever rendered when `onSelect` was set, and the
`renderEach` cases do not set it.
